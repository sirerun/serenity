## Why the transfer is feasible

AWS supports one-operation `PutObject` uploads up to 5 GB; objects above that can use multipart upload. Multipart supports 5 MiB–5 GiB parts and up to 10,000 parts; a 500,000,000,000-byte object needs 94 parts at 5 GiB each, or 7,451 parts at 64 MiB. Both fit the part-count ceiling. AWS CLI `s3api` exposes file-backed `put-object --body`, `upload-part --body`, conditional `put-object` and `complete-multipart-upload`, expected-owner parameters, and `get-object --version-id` with an output filename. Completion must check the actual CLI result: S3 may stream whitespace after an initial 200 and encode an error in the final response. [S3 upload limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html), [multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html), [AWS CLI upload-part](https://docs.aws.amazon.com/cli/latest/reference/s3api/upload-part.html), [AWS CLI conditional complete](https://docs.aws.amazon.com/cli/latest/reference/s3api/complete-multipart-upload.html), [AWS CLI version-pinned get](https://docs.aws.amazon.com/cli/latest/reference/s3api/get-object.html).

The bounded-development scope can be tested offline. A fake executable can record argv and its replacement environment, emulate version pages and conditional-write races, inspect file-backed bodies, and inject timeouts, malformed output, mutation, short writes, and cleanup failures. A sparse file slightly larger than 5 GB can exercise streaming and multipart routing without materializing the body in memory; hashing still has to scan the data. A 500 GB physical transfer, installed ARM CLI provenance, latency/cost, and actual IAM/bucket behavior remain separate operational evidence, as the proposed contract already says.

## Freeze blockers

1. **The inventory result cannot currently say which version is latest.** In PR344, `RemoteObject` has only `key`, `version_id`, and `delete_marker`; it drops S3's `IsLatest` field. `Storage.list_prefix` does not promise an ordering from which latest can be derived. The existing `_read_exact_keys` rejects all duplicate keys, so it cannot select a latest version from full history. Add a required `is_latest` field to `RemoteObject` and require exactly one latest entry per key, including delete markers; or specify and test a precise ordering contract that carries the same evidence. Prefer the explicit field. The new `read_bytes`/`read_to` version arguments are the right handshake, but every control and artifact read must receive the identity selected from the completed inventory.

2. **The described existing write interface does not match PR344.** The source protocol is `put_if_absent(key, source, *, length_bytes, sha256, chunk_bytes)`, not the contract's `length` spelling or the shorter argument list. State the existing signature exactly and limit the intended additive source changes to `read_bytes(..., version_id=...)`, `read_to(..., version_id=...)`, the latest-version metadata/selection behavior, and the required downloader ordering.

3. **Definite `ObjectExists` can be mistaken for a lost completion response.** `publish_snapshot` currently catches every exception from the final `COMPLETE` write and tries byte-equal readback reconciliation. A definite 412 should become `ObjectExists`; the current broad catch can accept an already-existing byte-equal COMPLETE, contrary to the contract's “ObjectExists as failure” rule. Permit a narrow publisher change to re-raise `ObjectExists` without reconciliation and reserve readback for genuinely ambiguous transport outcomes. Add a regression where the final key already has identical bytes and the adapter reports `ObjectExists`; it must fail.

4. **There is no public generic process-runner seam for the new operations.** `backup_retention_awscli.AWSCLIStorage` has public retention methods for version/MPU listing, parts, deletion, and abort, but `put-object`, `upload-part`, `complete-multipart-upload`, and versioned GET are absent. Its arbitrary `_run(operation, args, ...)` is private. The contract forbids changing that runner while asking for integration through its public runner contract. Choose one: authorize a narrow public file-backed S3 executor with an absolute-deadline parameter, or explicitly assign the new transport its own process runner and require parity tests for environment scrubbing, bounded output, wait/reap ownership, and no post-reap signals. Also define the whole transfer deadline versus per-child timeout: a fixed child timeout cannot be reduced to remaining operation time unless the runner exposes it. Keep CLI version provenance caller-attested and deployment-verified; code cannot inspect the actual version without launching a process, which conflicts with tests requiring invalid version configuration to fail before spawn unless the contract distinguishes config validation from binary qualification.

5. **Suspended versioning must be detectable before the first write.** The proposed behavior requires a hard refusal when versioning is suspended, but the allowed inventory flow does not explicitly query bucket versioning. An empty `ListObjectVersions` result cannot prove the bucket's current versioning state. Add a fixed, expected-owner `get-bucket-versioning` preflight and require `Status=Enabled` before any upload; deployment IAM must prevent suspension afterwards. Reject a `null` version ID as well. AWS documents that a suspended bucket creates null versions and that an expiration action can create a null delete marker. [ListObjectVersions response fields](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectVersions.html), [versioning-suspended lifecycle behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html).

## Boundaries to state more explicitly

- **Define “latest” at inventory time.** The required race test says that if a newer version appears after inventory, the reader still GETs the inventory-selected ID. That means “non-latest” refusal is evaluated against the completed inventory, while the subsequent version-ID GET deliberately reads that captured identity even if it is no longer current. Say this directly so the test and refusal rule do not conflict.
- **Keep all-history safety conditional on an external gate.** `If-None-Match: *` checks only the current version in a versioned bucket and can succeed when that current version is a delete marker. Complete inventory plus that condition is not atomic all-history absence. The contract correctly makes qualification conditional on an exclusive publisher writer and protections against delete, delete-version, versioning suspension, and admin changes. Also require no active lifecycle expiration/noncurrent-version rule on `snapshots/` that could add a delete marker or remove history during publication; allow only the required incomplete-MPU abort rule. S3 lifecycle expiration itself can create a delete marker, independently of the caller's IAM role. Fake-process races do not prove those deployed controls. [Conditional-write semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [lifecycle expiration behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html), [bucket-policy conditional-write enforcement](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html).
- **Name numeric operational ceilings.** The code must have concrete configuration and hard maxima for version/list pages, total versions and delete markers, total child invocations, aggregate wall time, stderr/stdout, and scratch bytes. The 1,003 publisher-object maximum and 500,000,000,000-byte snapshot ceiling are established; the remaining ceilings and part-size policy are not. A 64 MiB part is one possible choice that stays under 10,000 parts at 500 GB, but it implies up to 7,451 upload-part child invocations for one maximum-size object. A larger configured part reduces process count while increasing per-part scratch. Pick and test an explicit policy rather than leaving both unbounded by contract language.
- **Version-pinned download ordering needs an explicit algorithm.** The current `download_snapshot` reads COMPLETE and manifest before inventory. Revise it to list and validate the complete bounded inventory first; select exactly one `IsLatest` non-marker control version; read COMPLETE and manifest by those IDs; parse the manifest; then select and read each artifact by its inventory-selected version ID. Apply the same rule to final-COMPLETE reconciliation and post-write verification. When a version changes after inventory, use the selected ID and do not silently re-list and switch.

## Assessment of required tests and remaining qualification

The no-AWS fake-process suite is feasible and can meaningfully prove command construction, strict pagination, version-ID propagation, local spooling, request bounds, mutation detection, and process cleanup. The required 1,000-brain/1,003-key integration can run entirely against the fake CLI, though the contract should budget the resulting child-process count and runtime. Preserve private SSD fixtures and scrubbed test environments. No fake suite can establish S3's actual conditional-write race, bucket versioning/lifecycle policy, AWS CLI package/checksum on AL2023 ARM, credentials, installed process ownership, throughput/cost, or physical scratch headroom. Keep those in the later deployment-qualification checklist and do not describe the development result as an all-history or AWS-qualified guarantee.

I found no reason to block an authorized source assignment once the five freeze blockers are resolved. Until then, my verdict is **revise contract, then request coordinator freeze**.
