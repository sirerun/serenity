# T23.47 lifecycle assembly audit — 2026-10-01

Source reviewed: `b43b66938260b28cdd40e8e7185b3982723e8281` in an isolated worktree. This is an implementation-planning review, not acceptance evidence. T23.47 remains partial; T23.57 is marked planned, which does not demonstrate completion.

## Findings

The billing APIs exist, but production assembly does not call them. `billing.Service` implements `contracts.BillingReconciler` and `contracts.BillingCloser`; direct billing-package tests exercise both against local HTTP fixtures. `service.Assemble` instead calls `Gateway.RecoverDeletions` at `internal/hosted/service/service.go:259` before it constructs the billing service at lines 282–287. It mounts the billing handler, then constructs and mounts the partner service on the same gateway. No production caller of `ReconcileCustomer` exists, and the account-delete dashboard route calls legacy `CancelAccount` (`internal/hosted/dashboard/dashboard.go:468`) rather than `CloseBillingAccount`.

That ordering can purge data before provider closure. `Gateway.RecoverDeletions` enumerates `status='deleting'` accounts and calls `DeleteAccount` (`internal/hosted/gateway/lifecycle.go:172–215`); `DeleteAccount` marks the account deleting, deletes its brains and credentials, and finally marks it deleted (lines 115–170). Startup currently invokes this recovery before billing is available. The dashboard's legacy call also closes provider state before `Gateway.DeleteAccount` freezes the account, leaving a window for another checkout. The safe order is: durably mark deleting; wait for in-flight checkout work; call `CloseBillingAccount`; purge only on `CloseStatusClosed`. Pending or ambiguous closure must leave the account and its data in deleting/pending state for retry.

Reconciliation is similarly unwired after restore. `backup.Restore` leaves accounts `restore_pending` with free plan state; no service or CLI path subsequently calls `ReconcileCustomer`. Its contract explicitly permits bookkeeping for frozen restore-pending accounts without granting access. A startup or bounded retry lifecycle must use server-owned account IDs and leave entitlement state unchanged on provider unavailable/ambiguous errors.

The current billing service uses one `s.mu` across `ReconcileCustomer`, `Checkout`, and `closeBilling`, including provider requests (`internal/hosted/billing/billing.go:279`, `468`, `1213`). A background reconciler or deletion for one slow account can therefore block checkout and closure for every account. T23.47 step 7 requires account-scoped serialization and checkout rate limiting; this is a prerequisite to adding recurring reconciliation. The gateway's global `g.mu` in `ServeHTTP` protects handler/session cache work and is released at line 179 before request handling. Keep billing provider calls outside that critical section; do not place reconciliation or closure callbacks under it.

`Service.Close` currently closes gateway, pool, and store only (`service.go:332`). If assembly adds a reconciler loop, it needs a service-owned context, cancellation, and wait before closing those dependencies. Partner assembly must remain intact: the partner service shares the gateway and is mounted after billing setup at lines 290–298.

## Safe implementation sequence

1. In the T23.47 billing-owned files, replace the global provider-operation lock with per-account serialization and an account-scoped checkout limit. Add a deterministic test that holds a fake provider request for account A while checkout for account B completes. Preserve lock ordering across checkout, reconciliation, and closure.
2. In T23.57-owned `internal/hosted/service/**`, construct one billing service before deletion recovery and retain it on `Service`. Keep billing disabled behavior explicit: a deleting account with provider state must not be purged when closure cannot be certified. Add a service-level fake-provider seam available to assembly tests (the current unexported `Config.billingConfig` prevents an external-package test from configuring billing).
3. Route account deletion through a durable freeze followed by `CloseBillingAccount`, then call the existing gateway purge only after a closed result. Retry pending closure without losing the deleting account. Startup recovery must close every deleting account before `RecoverDeletions` can purge it. This requires a narrow gateway/dashboard integration handshake: T23.57's exclusive write scope excludes `internal/hosted/gateway/lifecycle.go` and `internal/hosted/dashboard/dashboard.go`; obtain explicit ownership for those files or define and review a service-owned deletion coordinator/interface before implementation.
4. Add a cancellable, bounded restore reconciliation lifecycle for `restore_pending` accounts, with sanitized failure recording and retries. Provider uncertainty must not activate accounts. Shutdown must cancel and join this worker before gateway, pool, or store close. Keep all provider work outside gateway cache locks.
5. Add assembled-service tests that prove (a) a deleting account is not purged while fake provider closure is pending, (b) retry closes provider state before purge, (c) restored accounts reconcile without activation on uncertainty and become eligible only on authoritative provider truth, and (d) the `/partner/` route remains mounted and uses the assembled gateway. Retain direct billing unit tests, but do not treat them as assembly coverage.
