## Concrete remaining gaps

- **Canonical operation identity and commit boundary.** `internal/hosted/gateway/gateway.go:376-438` creates/reserves an internal ledger record, but calls `EnterCanonical` at line 435 before invoking the memory tool at lines 447-452. The server validates JSON, required fact/provenance, TTL, kind, visibility, and entity in `internal/server/memory/remember.go:68-137`, so malformed/deterministically rejected requests can already be held as pending review. `internal/writer/memoryfact.go:84-99` already funnels writes through `Queue.Submit`; `rememberLocked` performs dedup checks and first writes the source at lines 105-165. The durable `operationRecord.ID` currently has no field in `MemoryFactPayload`; the source only carries the client-facing `OperationKey`, which is not canonical proof for the ledger row. Add an internal-only propagation seam and persist the ledger ID as a distinct canonical marker. Invoke `EnterCanonical` from inside the serialized queue job after validation/dedup/cancellation checks and immediately before first canonical source write. Keep provider work outside that serialized commit section. Caller-supplied JSON must never set the internal ID.
- **Fingerprint completeness and normalized input.** `gateway.go:393` fingerprints only brain and fact; T23.44 requires every stored remember field, including normalized TTL, provenance, entity, kind, and visibility (`tasks.json:182,188`). Gateway currently reserves before full normalization. Make validated normalized values the fingerprint source while preserving the server's public API semantics.
- **E24 reservation behavior.** Storage/memory limit rejection at `gateway.go:441-444` follows `EnterCanonical`; the deferred finalize path therefore sends an ordinary limit rejection to `pending_review`. Validate args and pre-mutation limits before entering canonical, and caller-release deterministic pre-canonical failures. Convert supported relative TTL shorthand to a fixed absolute value before forwarding (or otherwise ensure the ledger-only key is never interpreted as an explicit user key by remember).
- **Recovery and quiescence.** Contracts require `EnterCanonical` inside a brain commit section; expired rows are reconciled only while an exclusive `BrainFence` spans canonical inspection and ledger transition (`interfaces.md:130-139`). Current production references show no `CanonicalChecker`, `BrainFence`, `ReconcilePending` startup/ticker, `ResolvePendingReview` admin route, or T23.44 phase-hook call sites. A checker must examine both committed Git history and working-tree/touched queue state; any ambiguous state stays `Unknown`/held. Reconcile at startup and periodically, and provide the frozen admin resolution path without acquiring locks in an order that conflicts with `Runtime.Mutations` or the writer queue.
- **Storage admission remains conditional.** The local `StagingGate` is not wired to production and does not provide an OS-enforced limit. The interface packet requires allocated physical bytes (including Git/index/WAL/vector writes), a hard staging cap reserved before mutation, and a measured `MaxMutationStageBytes`; `FileInfo.Size()`/payload length and cooperative accounting are insufficient (`interfaces.md`, storage admission section; `result.json:36-47,77-93`). Implement a quarantine/staged writer seam plus OS-enforced staging and allocation measurement, or the contract's approved, measured per-mutation ceiling fallback. Until a measured bound and OS enforcement are reviewed, storage admission remains blocked; do not claim qualification or acknowledge writes past that gate.
- **Period-scoped client keys.** Current migration 4's partial unique key index is `(account_id,brain_id,client_key)` and excludes only released rows (`internal/hosted/store/migrations.go:38-64`); the ledger lookup also omits quota period. T23.44 requires period-scoped lookup (`tasks.json:182`). Migration 8 is already the ADR023 partner schema (`migrations.go:121-173`) and must stay intact. Any correction belongs in a forward migration 9, not a rewrite/reuse of migration 8.

## Minimal recovery sequence

1. Add a private trusted operation context/callback from Gateway to the hosted memory handler. Have the handler decode and normalize the request first; use the same normalized stored values for fingerprinting and the writer input. Keep the explicit client key separate from the ledger's internal operation ID.
2. Extend the canonical memory payload/projection with a distinct internal operation marker. Propagate it only through the private callback/context, never through client JSON. In `MemoryFact.Remember`, run `EnterCanonical` inside the existing `Queue.Submit` render after validation and duplicate/cancellation checks, before the first source byte. Preserve the marker when writing/replaying the canonical record and use it as the canonical outcome evidence.
3. Add focused regressions for malformed and limit-rejected requests leaving no held/pending-review row, relative TTL normalization, complete fingerprint conflict behavior, queue-boundary `EnterCanonical`, and restart-visible marker persistence. Keep indexing/provider work outside the canonical fence and avoid nested queue submissions.
4. Separately implement production canonical checker/fence and startup+ticker reconciliation plus pending-review admin resolution. Checker must treat uncommitted/touched operation-bearing paths as unknown, never absent. Wire the existing hosted phase barriers and production-inert test guard.
5. In a separate schema-owned change, period-scope active client keys with forward migration 9 while preserving migration 8. Verify rollover/released-row behavior against existing ledger suites.
6. Keep the physical-storage criterion blocked until an approved staging seam, allocation measurement, and OS quota are integrated and independently reviewed. Then rerun the complete T23.44 acceptance matrix and replace the PARTIAL evidence with a new source-pinned receipt; do not edit frozen interfaces/registry to lower the bar.
