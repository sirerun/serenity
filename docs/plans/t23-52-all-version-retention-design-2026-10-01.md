# T23.52 all-version retention design — 2026-10-01

Source baseline: canonical origin/main at 230234c969058807236af76d91da0967357a37cd (PR #332). This is a read-only implementation design. It does not claim T23.52 acceptance and made no AWS/API calls or object deletions.

## Contract and main design

T23.52 is planned and owns deploy/hosted/backup.sh, purge.py, backup/purge service and timer units, and test_backup_retention.py (docs/tasks/hosted-completion/T23.52.md). It requires an hourly scheduled all-version purge, dry-run inventory, exact stack-owned scope, failure on malformed time/pagination/permission, no successful receipt while eligible versions survive, and oldest-surviving-age reporting. The customer-facing rule in ADR 019 is backups expire within 31 days. The task's recommended operational target is a 29-day eligible age plus an hourly sweep, with a failed purge reported as failure rather than a 30-day promise.

Use the fixed S3 namespace snapshots/, with generated snapshot prefixes exactly snapshots/YYYYMMDDTHHMMSSZ/. At process start, take one timezone-aware UTC now; set cutoff = now - 29 days. A valid snapshot prefix becomes eligible when its parsed UTC timestamp is <= cutoff. Purge the entire eligible prefix as one retention unit, including every current/noncurrent version and delete marker, whether or not it has COMPLETE. The prefix timestamp is the capture/source age; retain each S3 LastModified too for the exact inventory and oldest-version report. A rewrite of a key inside an old snapshot prefix must not extend that snapshot's retention.

For an on-time hourly sweep, maximum wait to the next start is under one hour. If an eligible prefix is fully purged within 22 hours of that start, total age at removal is under 29 days + 23 hours, leaving one hour of margin inside 30 days and over a day inside ADR 019's 31-day bound. Make the service a bounded one-shot with a hard runtime cap and never return success at that cap with eligible records remaining. The cap must be load-qualified against inventory and request counts; if the sweep fails, is delayed, or misses its bound, persist a failed status and alert. A 29-day threshold and timer alone cannot promise deletion during outages or a long/unbounded run. Persistent=true catches up one missed activation after host downtime but does not make a failed sweep succeed.

## Listing, planning, and apply flow

1. Read only the bucket pinned by trusted deployment config and always supply its expected owner account ID where supported. Fix the list prefix in the program to snapshots/; reject any caller override, empty prefix, other namespace, or mismatch with the stack output. Never accept bucket/prefix strings from an untrusted command input on the scheduled apply path.

2. In --dry-run (the default), enumerate with aws s3api list-object-versions --no-paginate --max-keys 1000 --prefix snapshots/. Parse both Versions and DeleteMarkers. When IsTruncated is true, require valid next KeyMarker and NextVersionIdMarker, pass the exact pair on the next call, and reject missing, repeated, malformed, or cycling continuation coordinates. Validate every returned key lies under exactly one valid timestamp prefix; parse timezone-aware LastModified, VersionId, IsLatest, and delete-marker type. Preserve "null" as an exact version ID if returned. Any malformed/foreign key or timestamp, API/JSON/XML error, denial, or incomplete listing makes the whole run fail closed; it must not skip a bad page and call the result complete. ListObjectVersions documents the paired key/version continuation markers and requires s3:ListBucketVersions.

3. For each eligible timestamp prefix, produce a canonical private JSON plan sorted by key and version ID. Include expected bucket owner/name, fixed prefix, UTC cutoff and generation time, each exact key/version ID, delete-marker flag, S3 LastModified, parsed snapshot timestamp, and plan SHA-256. Keep exact opaque keys/version IDs in a mode-0600 plan/report under task-owned private runtime storage; log only counts, plan digest, oldest age, and fixed failure class. Dry-run performs no Delete or Abort API call.

4. --apply must be explicit and separately recorded. Manual apply should require the hash of the reviewed plan and refuse if the plan's bucket, owner, prefix, cutoff or current inventory has changed; it can generate a new plan rather than broaden the old authorization. The reviewed systemd timer can carry a fixed standing policy (owner-pinned bucket, snapshots/, 29-day cutoff and once-hourly invocation) and records the per-run plan hash before deleting. Recheck cutoff and prefix on every candidate immediately before action. Never issue an unversioned delete: batch exact {Key, VersionId} pairs, at most 1,000 each, using verbose DeleteObjects responses; reject any per-object error or unexpected result. A versioned delete request requires s3:DeleteObjectVersion; an ordinary unversioned DELETE would create a marker instead of erasing prior versions. After batches, fully re-list snapshots/; a success receipt is allowed only when a fresh complete inventory shows no version or delete marker in any eligible prefix. If a concurrent eligible version appears, re-plan and apply only within the same fixed policy, or fail for a new explicit approval; never silently leave it.

5. Enumerate incomplete multipart uploads separately using aws s3api list-multipart-uploads --no-paginate --max-uploads 1000 --prefix snapshots/. Follow the exact NextKeyMarker and NextUploadIdMarker pair on truncated pages, rejecting absent/repeated markers and errors. Validate every upload key has a valid snapshot prefix and a timezone-aware Initiated timestamp. Abort uploads whose Initiated <= now - 1 day (matching the stack's configured 1-day multipart cleanup), including stale uploads in recent snapshot prefixes; do not abort a recently initiated upload. After abort, use ListParts to prove parts are gone; AWS documents that in-flight parts can still succeed after abort and that repeat abort/ListParts checks may be needed. Bound retries, and fail/alert if parts remain. The plan records both snapshot prefix time and MPU initiation time.

6. Only record successful completion after all version pages and multipart pages complete, all eligible exact versions/markers have been deleted without per-entry errors, all eligible multipart uploads are gone, and the post-delete inventory proves none remain. Report snapshot count, exact versions/markers deleted, MPU outcomes, oldest surviving valid snapshot timestamp age, and oldest surviving S3 LastModified age. If version inventory is empty, distinguish a valid empty result from missing/malformed API inventory; never turn a denied/truncated read into an empty success.

The helper added in PR #332 is a local marker checker only; current backup.sh still uploads recursively and writes a timestamp-only COMPLETE, and the helper is not wired into upload/restore/purge. The future backup path must upload verified artifacts and the manifest first, then the helper's exact manifest-bound completion record last. Retention can enumerate/purge by timestamp prefix without treating COMPLETE as authority; it must still clean every version in an expired incomplete prefix.

## Age bound, lifecycle, and deletion journal

The 29-day cutoff gives a successful hourly run up to nearly 23 hours after becoming eligible to finish inside 30 days. A hard 22-hour run cap leaves an additional one-hour margin. This is a scheduled-policy bound under synchronized UTC, uninterrupted service availability, successful APIs, and a full sweep within the cap—not a guarantee through persistent API denials or host outages. Such failures must break the purge status and invoke the delivered purge failure >=1 alarm; do not emit a 30-day success/promise for them. Task66 must exercise the real API on disposable prefixes and test the 31-day acceptance; this design does not authorize production deletion.

Current deploy/hosted/stack.json has one versioned Backups bucket with an unfiltered lifecycle rule: current ExpirationInDays: 30, noncurrent NoncurrentDays: 30, and abort-incomplete-multipart after 1 day. That can retain noncurrent backup versions for roughly 30 days after the current-version expiration marker, so it is not the ADR 019 backstop. T23.54 expressly owns stack.json and requires noncurrent expiration 1 day. Its change should scope every lifecycle action to snapshots/, use NoncurrentDays: 1, retain current 30-day expiration, separately remove expired delete markers under snapshots/, and scope the 1-day multipart abort rule to snapshots/. Lifecycle is asynchronous and a backstop; the active purge and oldest-age report remain authoritative. AWS documents that expiration of a current version in a versioned bucket creates a delete marker, while noncurrent versions require their own expiration action and lifecycle work can be delayed.

The frozen journal contract in docs/launch/hosted-completion/interfaces.md says no lifecycle rule applies to deletion-journal/ and backup purge jobs never list, expire, or delete that prefix. Keep this purge's API requests hard-coded to snapshots/; do not add journal list/delete permissions or a journal-GC fallback. T23.52 also says to apply a later minimal-metadata journal retention after protected snapshots disappear; that conflicts with the current frozen journal interface's separate-retention decision. Resolve through the T23.48/T23.54 contract owners before any journal retention work; T23.52 should leave journal objects untouched.

## Precise T23.54 IAM and alarm/unit request

stack.json currently gives the Backups bucket s3:ListBucket and grants s3:GetObject/s3:PutObject on the Backups object ARN wildcard; it has no version listing, version deletion, multipart listing/abort, or part-list permission. T23.54 owns that file and requires least-privilege versioned-object access. Request:

- On the Backups bucket ARN, add s3:ListBucketVersions with s3:prefix constrained to snapshots/* (AWS explicitly supports this condition for version listing). Add s3:ListBucketMultipartUploads only if the multipart inventory remains in scope: the current S3 authorization reference gives that action no s3:prefix condition key, so IAM cannot constrain that list action to snapshots/*. The CLI/API request must still use the hard-coded snapshots/ Prefix and tests must prove it never requests deletion-journal/. If strict IAM-level namespace separation is required, the choices are a separate object bucket/credential boundary or relying on the snapshots-scoped lifecycle rule for incomplete multipart cleanup instead of active ListMultipartUploads; resolve that contract tradeoff with T48/T54 before granting broader listing.
- On object ARN Backups ARN plus /snapshots/*, allow only versioned retention operations: s3:DeleteObjectVersion, s3:AbortMultipartUpload, and s3:ListMultipartUploadParts for the post-abort verification. Grant no s3:DeleteObject to the retention path; code always supplies version IDs. Keep s3:DeleteObject and all deletion actions denied on deletion-journal/*.
- Keep existing GetObject/PutObject backup and journal permissions separate by snapshots/* vs deletion-journal/*; do not widen to s3:*, account-wide objects, or journal deletion. T54 should decide whether a separately scoped purger role is practical within the approved credential boundary; do not work around IMDS/network restrictions to assume a role.
- T23.53/T54 should expose a fixed-dimension purge failure count and last-success timestamp/age, with the existing task54 purge failure >=1 delivered alarm and a stale-success/oldest-backup-age breach. Never use account, brain, key, or version IDs as metric labels. The oneshot service uses a nonzero exit on list/delete/verify failure, a hard timeout shorter than 22h, and an OnFailure route to the approved delivered destination. The hourly timer is persistent; task57 wires installation and task64 proves it actually fires and delivers the alarm.
- T23.60 should include paginated version-list calls, MPU-list/ListParts calls, version delete batches, abort retries, and lifecycle/API request amplification in its cost model.
