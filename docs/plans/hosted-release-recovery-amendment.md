# Explicit expired-pending release recovery

Status: source amendment authorized by coordinator within the owner-approved implementation scope; independent exact-head review remains required. No trust policy, signing call or production state is activated.

A prepared deployment can remain pending beyond the signed manifest expiry after an interrupted installation. Ordinary promotion and rollback retain strict current expiry checks. Recovery of this exact existing transaction may use an independently installed, freshly valid root approval with mode recover-promote or recover-rollback, all ordinary exact artifact/source/archive/sequence/previous-state fields, and additional pending_sha256 and installed_manifest_sha256 fields. These bind the exact canonical durable marker and the operator-verified installed manifest. The explicit recover command also requires the same installed manifest pin as a separate argument.

Only this extended canonical approval schema authorizes temporal reapproval. Its issuance/expiry window must be currently valid; an expired approval is never accepted. The manifest must have a valid, bounded, canonical original issuance/expiry chronology, and issuance cannot be in the future. Only elapsed artifact expiry is waived. Verification still uses the currently installed policy and key, real ECDSA signature, exact streamed archive hash/size, pending previous state and monotonic transition rules. An old or revoked key never becomes trusted through recovery approval.

Ordinary verify, prepare and commit reject extended recovery approvals. Recovery cannot select a new artifact, create a pending marker, infer installed identity, weaken high-water rules, authorize an arbitrary rollback or remove an unrelated pending marker. A crash after persisting the exact next state can only finalize that same pending transition. The trusted operator remains accountable for establishing actual installed identity and compatible runtime/data state before supplying the pin.

Regression coverage includes expired artifact with fresh exact recovery approval, promotion and rollback high-water preservation, existing ordinary recovery behavior, expired/future approval denial, ordinary-mode rejection, pending/state/source/archive/sequence mismatch, corrupt signature/archive, current key revocation, future manifest, invalid original chronology and post-state-write reconciliation. Tests use software keys and temporary root-owned state; they do not establish provider or deployment acceptance.
