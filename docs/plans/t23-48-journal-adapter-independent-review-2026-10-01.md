**Reviewed candidate:** `82763466b4b33679508350803041b327c458e8f7`, isolated worktree `review/t23-48-journal-adapter-20261001`. The source branch later added documentation-only module evidence; the reviewed adapter code is unchanged. This is a local code review, not T23.48 acceptance, production assembly, or AWS qualification.

## Verdict

**Do not merge the adapter as ready for integration until the resume-after-seal defect is fixed and regression-tested.** I reproduced a valid journal object after a seal being accepted by `ReadThrough` when resuming from that seal. The result is returned with `Sealed=false` instead of `ErrDeletionJournalFenceViolated`, contrary to the frozen interface. I also reproduced a separate lower-generation completeness ambiguity: with a journal configured for generation 3, a generation-1 seal and a missing generation 2 cause `ReadThrough(zero)` to return the generation-1 seal as `Sealed=true`, without noticing a valid generation-3 object. T50 must bind its recovery decision to an authoritative generation and verify the full predecessor chain; a lower seal cannot be treated as the adopted generation's complete tail.

Resume loading also checks that the decoded object coordinates match the coordinates in the requested watermark and that its stored-byte hash matches `EntryHash` (`internal/hosted/deletion/journal.go:267-282`). The new shape cases cover unknown kind, malformed entry, a seal carrying entry fields, and malformed resume objects (`internal/hosted/deletion/journal_shape_test.go:34-137`). Existing conformance cases cover missing middle/tail, replaced objects, wrong watermark hash, object beyond seal, and generation rollover (`internal/hosted/contracts/contractstest/journal_suite.go:102-151,174-269`).

## Blockers and integration boundary

1. **Resume after seal is not fail-closed.** `ReadThrough` initializes `res.Sealed` from the watermark's object kind, but then calls `readGen` after that sequence (`journal.go:267-297`). `readGen` begins with `sealed := false` (`journal.go:143-150`), losing the fact that the predecessor object was a seal. I inserted a structurally valid next entry whose `PrevHash` is the seal hash. `ReadThrough(ctx, sealWatermark)` returned nil error and the new entry, clearing `Sealed`. The contract explicitly requires any object beyond a seal to return `ErrDeletionJournalFenceViolated` (`docs/launch/hosted-completion/interfaces.md:178`). This is a concrete adapter blocker and needs a regression for a valid post-seal entry when the read starts at the seal watermark; the current beyond-seal test starts from zero and does not cover it.

2. **Configured-generation completeness requires a caller-bound authority check.** `ReadThrough` only probes `gen+1` after the current generation (`journal.go:305-325`) and does not use `j.gen` as an expected generation. A test with `Journal(... generation=3)`, a valid generation-1 seal, an absent generation 2, and a generation-3 entry linked to a removed generation-2 seal returned `Sealed=true` at generation 1. The accepted protocol promises sequential generation traversal and rejection of a generation that began without its predecessor sealed (`interfaces.md:179`); more fundamentally, recovery must not treat the last visible lower-generation seal as the adopted generation's full tail. T50 should compare the read/seal receipt with an authoritative expected generation and validate every predecessor seal before unfreezing. Until that caller gate exists, the adapter's `Sealed` bit alone is insufficient evidence of current-generation completeness. Do not claim this library proves an authoritative generation from the highest visible prefix.

`NewAWSJournal` uses `config.LoadDefaultConfig` (`internal/hosted/deletion/config.go:26-51`), whose default AWS chain can attempt instance metadata. The hosted app unit denies IMDS, while the backup unit retains it under ADR020. The constructor comments correctly disclose that an independently scoped credential source is required. No cloud API, service, or stack action was made. The AWS qualification test was not enabled. The adapter can be merged as an unused library only with its pinned SDK module dependencies and without claiming production wiring or qualification; do not call `NewAWSJournal` from the hosted app until credentials are explicitly scoped to work with the IMDS deny.
