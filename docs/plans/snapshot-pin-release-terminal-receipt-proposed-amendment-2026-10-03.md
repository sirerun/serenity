## Exact wire-compatible rule

After a valid RELEASED tombstone is durably published, the live lease is absent, and exact CompletePinRelease returns nil, retain `.releases/<lease-id>/release.json` and its captured containing directory as the permanent producer-side terminal receipt for that committed attempt. Do not remove the directory or release.json. The RELEASING lease.json may be removed with exact identity and required sync only after the existing reviewed ordering permits it; unknown or replaced temp entries are not guessed cleanup targets. No new state, file name, field, owner API or public authority is introduced. The local receipt is integrity/correspondence evidence, never release authority.

Subsequent Reconcile validates the complete owner attempt list and exact local receipt tuple, stable root/journal/receipt-directory identity, and absent live lease, then calls exact CompletePinRelease idempotently. An already RELEASED owner acknowledges nil; RELEASING may finish only after verifying the exact backup tombstone. Errors, cancellation, unknown/mismatched history, live/replaced/symlinked lease, or identity mismatch refuse without deleting receipt or snapshot bytes. This is the existing Branch B terminal path with no receipt deletion afterward. Do not omit released committed attempts from the authoritative owner response, skip missing pair validation, or fabricate a receipt after all correspondence has already been lost. Existing no-receipt orphan state remains a fail-closed operator recovery gap, not automatically repaired.

## Bounds and retention consequence

Current usageLocked already charges a valid terminal tombstone MetadataBytes to retained metadata without counting it as a live artifact lease. Preserve and test that accounting; repeated terminal acknowledgement adds no files/bytes and cannot recycle owner tuples or historical capacity. Future Stage refuses before publication when the configured retained metadata ceiling cannot fit the new reservation. Retained terminal receipts and in-progress direct journal entries together have a fixed protocol ceiling of 4096 entries (a new private producer constant matching the existing maximum owner-attempt response ceiling, not a public configurable option). Both usageLocked and finishReleaseJournal must use a fresh identity-validated journal-directory descriptor and bounded ReadDir(4096+1), refusing before processing if more than 4096 entries are returned. Existing os.ReadDir calls are unbounded and must be replaced. Unknown, noncanonical, symlinked or non-directory direct entries fail closed untouched; no ignored hidden-entry escape. Count every direct entry toward the ceiling before semantic validation. Stage refuses before creating/publishing any new snapshot when the journal is at the ceiling; release refuses before starting a new entry at the ceiling unless it is an exact existing idempotent marker/receipt. All scans revalidate captured root/journal identity before and after enumeration. Add no zero-as-unlimited or automatic compaction/purge. Logical accounting is not a physical quota or permission to delete history. The system intentionally has finite terminal history capacity until a separately reviewed compaction/migration contract exists.

Do not enlarge options or change wire/schema. If terminal receipt publication cannot fit an already guaranteed metadata reservation, refuse before starting release, retaining the original complete pin/lease. Required release metadata headroom must be checked before starting release and again before destructive deletion: encode the prospective canonical live RELEASING record, marker record, final RELEASED receipt and required temporary writes using the real encoders; conservatively reserve their entire simultaneous footprint in addition to all unrelated retained metadata, avoiding double-counting an already charged exact existing marker only with a validated identity/tuple. Charge current live metadata, marker and scratch until each is actually replaced or removed; do not treat future removal as available current headroom. Arithmetic must be checked for overflow. A conservative over-reservation is safe but must be disclosed; no under-accounted peak is accepted. No success receipt or cleanup may rely on exceeding the configured cap. Exact root/lease identity and owner authority remain required independently of capacity.
