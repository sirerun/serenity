## Exact source seams and next work

### Immediate coding boundary: testable, unused publisher

T23.52 can start a separately testable publisher boundary such as `deploy/hosted/backup_publish.py` (add it to T23.52's explicit ownership) while production authority inputs are resolved. Give it an injected object-store transport so local fixtures can exercise every operation without credentials. Its input must be an immutable, already-created manifest-v2 snapshot from the trusted backup coordinator; it must never create a watermark, substitute a timestamp marker, or accept a legacy snapshot. Keep this publisher unreferenced by the installed `backup.sh` and service until the production journal/admission/credential factory and T23.54 deployment inputs are supplied. This boundary is useful implementation progress, not end-to-end or T23.52 acceptance.

The publisher's required invariants are: (a) one serialized run under an exclusive lock; (b) caller-owned private staging with headroom checked before snapshot creation and cleanup limited to that run's files; (c) snapshot creation through the admitted service path so the manifest retains the durable deletion-journal watermark, with no synthesized/zero watermark or filesystem journal fallback; (d) reserve a fresh, non-reused snapshot prefix and freeze the snapshot contents for the full operation; (e) verify the local v2 manifest and every declared artifact before any publication; (f) upload exactly those artifacts and `manifest.json`, then read back and verify all remote bytes against manifest path/length/SHA-256; and (g) upload the exact manifest-bound `COMPLETE` record only after remote readback passes, as the final remote write. Missing/invalid completion must never fall back to the legacy timestamp marker. Any pre-completion error leaves no valid completion record, returns failure, and records failure/age status. If the final write's response is ambiguous, fetch the exact remote record and verify it with the manifest and artifacts before deciding success; if that cannot be proved, return failure. Tests at this boundary can establish interruption and tamper rejection, but cannot establish trusted snapshot provenance or deployed-object-store behavior.

1. **Upload and completion (`deploy/hosted/backup.sh`, owned by T23.52).** `backup_completion.verify_completed(snapshot, prefix)` verifies the exact version-2 manifest, its declared artifact lengths and SHA-256 hashes, exact directory membership, and the completion record's manifest hash and snapshot prefix. `create_completion(snapshot, prefix)` makes that local record safely and refuses a changed/invalid snapshot. The current shell script instead calls `aws s3 cp --recursive`, then uploads a temporary text file containing only the timestamp as `COMPLETE`. Replace that path with a serialized single-run pipeline: private caller-owned outer staging; establish local disk headroom; create the snapshot; call the helper to verify/seal it; upload only the manifest-declared artifact files and manifest; verify remote bytes against the manifest (download to private verification staging and call `verify_completed`, or an equivalently strong checksum verification); then upload the exact bound completion record as the final remote object. Do not publish `COMPLETE` on any upload/readback error. Record failure and age metrics on every unsuccessful path. Keep the backup lock held through verification and publication, clean only this invocation's staging, and retain existing snapshots on failure. `systemd` serializes activations of one service unit, but does not by itself serialize a manually invoked script; the script needs an explicit process lock. Current `serenity-backup.service` has a private umask and timeout but no disk-headroom check or script-level lock.

2. **Remote download and restore (ownership gap).** No downloader exists in `deploy/hosted`; `internal/hosted/backup.Restore(ctx, snapshot, destination)` validates a local directory and stages/publishes restore atomically, but there is no S3-to-private-staging path that requires `COMPLETE` before handing bytes to it. T23.52 requires interrupted uploads to be rejected by the downloader, while its exclusive file list does not name a downloader file. Coordinator must assign this path explicitly: either extend T23.52 ownership for a narrowly named remote fetch/verify helper and test, or assign the adapter to the T23.49 backup owner with a reviewed interface. Fetch `COMPLETE` first only as an untrusted discovery record; fetch the manifest and every declared artifact into a fresh private directory, reject missing/extra objects, then call `verify_completed` with the exact expected timestamp prefix before calling Go `Restore`. Never expose the destination until verification succeeds. A timestamp-only or absent marker must fail closed. T23.49's task file and registry still say `planned`; its current Go implementation is useful but not proof that its dependency acceptance and journal watermark inputs are qualified.

3. **Retention inventory and purge (`deploy/hosted/purge.py`, T23.52-owned).** `backup_retention.inventory(storage, bucket, expected_owner, now)` performs bounded complete inventory of versions, delete markers, and multipart uploads and returns a canonical hashable `Plan`; `serialize_plan`/`load_plan` preserve a reviewable exact inventory; `apply(..., approved_sha256, bucket, expected_owner, now)` re-inventories, checks the approved hash and unchanged inventory, deletes exact version IDs, aborts stale multipart uploads, and fails unless a fresh post-inventory proves no eligible data remains. This is a solid seam for a dry-run CLI and report. Implement `purge.py` to fix scope to `snapshots/`, accept only deployment-pinned bucket/expected-owner config, emit exact keys/version IDs/source timestamps and plan hash in dry-run, and keep dry-run free of destructive calls. The existing `AWSCLIStorage` implements the protocol but requires explicit trusted executable, region, bucket, expected owner, temporary credential mapping, time/output bounds; it is not wired or qualified. Its destructive methods must remain unreachable until config provenance and apply authority are settled.

4. **Destructive apply authority and audit record.** The library's `approved_sha256` is a plan comparison, not proof of who approved deletion. T23.52 requires recorded destructive-action authority. There is no authority-record schema, trusted principal, or durable pre-delete record interface in the current helper seam. Request a coordinator/T23.54 ruling that defines the authorized standing scheduled policy versus manual reviewed-plan approval, trusted owner identity, where the plan hash and authority decision are durably recorded before first delete, and how failures are recorded. The scheduled policy can be a fixed reviewed scope (`snapshots/`, owner-pinned bucket, 29-day prefix cutoff, one-hour schedule) only after that authority is explicitly approved. Do not treat possession of AWS delete credentials or a hash flag as approval.

5. **Installable purge schedule and observability (`serenity-purge.service`, `serenity-purge.timer`, T23.52-owned; task57 installs, task64 qualifies runtime).** Neither unit exists. Add a bounded oneshot and persistent hourly timer. Service must fail nonzero on incomplete inventory, API denial, malformed data, delete mismatch, timeout, or eligible data remaining, route `OnFailure` to the already approved delivered alarm, and write a successful receipt only after post-inventory. Report oldest surviving snapshot-prefix age and object last-modified age, along with bounded counts/hash and fixed-dimension status metrics. Use the reviewed 29-day eligibility point plus hourly execution and a load-qualified hard run bound; the existing lifecycle policy is only a backstop. T23.57 owns install wiring and T23.64 owns proof it actually fires/delivers alerts, so request the exact unit names, enablement/install hook, failure destination, and metric sink contract from those owners before declaring operational acceptance.
