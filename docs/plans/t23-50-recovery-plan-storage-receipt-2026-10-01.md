# T23.50 immutable recovery-plan storage receipt

Source base: main337 `06e22d019dccd04963f6309c13e0b45f441c7e8a`. Candidate source at receipt preparation: `363e2f040d7f1fe44e7c94ab98f134e69c3caff3`.

This bounded prerequisite adds `internal/hosted/recovery` plan persistence only. `CreatePlan(ctx, dir, input)` canonicalizes a sorted, unique account scope and persists an immutable, hash-named JSON artifact. Its SHA-256 covers canonical payload fields excluding the hash: format version, supplied exact manifest-byte SHA-256, deletion-journal watermark, fence generation, UTC provider observation time, and account IDs. `LoadPlan(ctx, dir, expectedHash)` reloads only that approved hash and validates the hash, canonical bytes, field relationships, and account scope. The decoder bounds file/account count and rejects duplicate keys, unknown or case-aliased fields, malformed nested objects, and trailing JSON. Plan directories must be absolute, private mode 0700, current-user owned, non-symlink directories with a safe immediate parent; plan files are opened without following symlinks and must be private regular files. Publication uses a synced same-directory temporary file, atomic no-overwrite hard link, and directory sync. Existing byte-identical plans are idempotent; corrupt or conflicting paths are never replaced. Platforms without the required safe filesystem support fail closed.

Verification passed on the isolated main337 clone: `go test -race ./internal/hosted/recovery -count=1` (`ok`, 3.650s), with external `TMPDIR`, `GOMODCACHE`, and `GOCACHE`; sampled one-minute load was 8.50 and no shared build lease was needed for the single package. Tests cover create/load/hash stability, sorted scope, idempotent create, wrong approved hash and modified payload, duplicate/unknown/case-alias/trailing JSON, corrupt-file no-overwrite, symlink target and plan-directory refusal, cancellation before I/O, and malformed digest/scope/time/generation.

This package does not read a snapshot, compute or authenticate the supplied snapshot digest, obtain provider truth, establish operator approval, seal or adopt a journal generation, revoke old credentials, plan, apply, activate accounts, or register a CLI command. `SnapshotSHA256` is deliberately distinct from build identity; the future planner must derive it from the exact manifest-v2 bytes and must not silently coerce it into the frozen `contracts.RecoveryPlan.SourceSnapshot` field. The payload hash detects artifact changes but is not a signature or proof of truth. Existing `LifecycleDependencies.RecoveryAdmission` and provider-free filesystem-journal test fakes remain unchanged and do not authorize production startup. T23.50 remains partial pending authenticated snapshot/provider inputs, explicit old-writer stop and credential/session revocation, durable seal plus successor-adoption evidence, service/CLI integration, and operator-controlled qualification.
