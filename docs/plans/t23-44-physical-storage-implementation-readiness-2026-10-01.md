## Outcome

T23.44 physical storage admission remains blocked. The repository has an in-process `operation.StagingGate` that accounts reservations, a cooperative `StageMeter`, and filesystem-oriented backup/snapshot code, but no production wiring from the Gateway through a staging gate, no concrete allocated-block meter, no enforced stage quota/filesystem, and no measured `MaxMutationStageBytes`. The T23.44 receipt calls this acceptance `BLOCKED`; it has not been superseded by later commits.

The repository-defined deployment topology declares one 30 GiB encrypted gp3 data volume formatted ext4 and mounted at `/var/lib/serenity`, with a separate 8 GiB root EBS volume. `bootstrap.sh` does not request `prjquota`, create a stage mount, or set quotas. `serenity-hosted.service` runs as unprivileged `serenity` with writes to `/var/lib/serenity`. `serenity-backup.service` also runs as `serenity`; `backup.sh` makes a full temporary snapshot under `/var/lib/serenity/.backup-*` on the same data filesystem. The stack defines no staging EBS volume or dedicated staging filesystem. No production `StagingGate` caller or storage-boundary adapter is present (`ReserveStage`, `AdmitMeasured`, `StageMeter` references outside contracts/tests are limited to `internal/hosted/operation/staging.go`).

The repository-defined topology can host an OS enforcement boundary, but its bootstrap/unit definitions do not provision a stage quota or stage mount. Whether a currently running host has separately configured enforcement is unverified. A 30 GiB data-volume ceiling is an eventual `ENOSPC` bound for the whole mount; it does not enforce `StagingBudgetBytes`, reserve `OperatorHeadroomBytes`, or keep per-account mutation admission below published storage quotas. The repository-declared 8 GiB root volume is not a safe place for customer mutation stages: it is a separate system filesystem and is not the persistent data mount.

## Exact gaps in the existing mechanisms

`internal/hosted/contracts/storage.go` requires the gate to reserve a fixed maximum before writes, count outstanding ceilings against global stage budget and free capacity, account allocated physical bytes (blocks/metadata/Git/index/WAL/vector), and keep operator headroom. It explicitly says `StageMeter` is cooperative, not a hard bound. `internal/hosted/operation/staging.go` implements the in-process arithmetic only: `Free` and `Physical` are callbacks; they are not bound to a kernel quota, mounted stage root, or physical-allocation source. Its state is in memory and has no startup recovery for a process crash with stage bytes left on disk.

`internal/hosted/backup/backup.go` makes a sibling `MkdirTemp` under the destination parent, vacuums the control DB, writes one Git bundle per ready brain, creates a temporary bundle-verification repository, and atomically publishes the snapshot. That staging is logical temp-directory discipline, not an OS byte limit. `backup.sh` chooses a temporary location under `/var/lib/serenity` and retains a complete local snapshot for upload, also without a physical cap.

`internal/hosted/backup/snapshot_inspect.go` requires private roots and checks an approved manifest digest; `declaredArtifactSize` caps the sum of declared artifact lengths and copy helpers cap bytes copied. Those are valuable input limits, but a manifest length/copy limit is not an allocated-byte or filesystem quota. `git bundle verify`/clone can create Git metadata in scratch, and SQLite/WAL/metadata allocations are not bounded by summing artifact `LengthBytes`.

There is an additional boundary to resolve before calling a complete mutation stage: ADR025 makes the hosted source fact canonical first and performs optional embedding/indexing afterward, outside the canonical commit fence. ADR017 still requires index/vector/WAL growth in the physical storage accounting. An OS cap on only a temporary Git/source directory would therefore miss derived-index writes. Either the stage boundary must encompass the actual growth of every relevant data class, including the postcanonical index path, or the integrator must approve a separate, equally bounded quota/accounting treatment for those writes. This is an explicit design seam, not permission to remove the index from product storage accounting.

## Concrete OS enforcement options

**Recommended first Linux path for the current single-node deployment:** use an ext4 project-quota hard limit on one root-provisioned staging directory on the existing `/var/lib/serenity` filesystem. Enable and verify ext4 project-quota support at provisioning, assign one fixed project ID with inheritance to the stage root, set its hard block and inode limits from the frozen global staging budget (with filesystem metadata/rounding allowance), and expose that root read-write to the service. The intended service process remains unprivileged and should not be able to alter the quota. The privileged installer owns quota setup; the runtime capability check must verify the expected mount/device, filesystem, project ID, hard limit and active enforcement. If the filesystem lacks project-quota support, quota state cannot be verified, or the mount/project/limit differs, stage reservation fails closed with a specific enforcement-unavailable error. Do not fall back to `StageMeter`, file lengths, or raw `statfs` free bytes as enforcement.

A same-filesystem quota root avoids another cloud volume and lets the staged-writer seam keep temp files on the data filesystem. It still requires the approved Git quarantine/staged writer change: all stage writes must actually be routed beneath the constrained tree, and publication must transfer canonical Git objects safely without leaving them charged to the transient stage project forever. Use an explicit core-writer publish operation (copy/unpack immutable quarantine objects into the canonical repository, then update refs under the existing narrow commit protocol) rather than assuming cross-project rename will preserve correct accounting. Stage cleanup on restart must wait for the operation ledger/checker to distinguish safely discarded work from committed/unknown work.

A dedicated ext4 stage EBS filesystem is a simpler enforcement primitive if the writer seam cannot use a quota-managed directory. It is an infrastructure/topology change: the current stack has no such volume, so attaching and mounting one costs capacity/spend and must be owned and approved by infrastructure. A stage volume's filesystem capacity hard-caps staged allocation but lives on a different filesystem; rename is not an atomic publish across filesystems. The writer must copy/publish safely and keep a separate reservation for the destination data EBS. Either option needs a plan for the existing local full-snapshot backup stage and operator headroom; neither should silently count backup temp as customer stage or ignore it.

On Linux, ext4 project quotas are kernel-enforced per project and may cap blocks/inodes. The [Linux ext4 administration guide](https://www.kernel.org/doc/html/latest/admin-guide/ext4.html) describes filesystem quota support, and [`quotactl(2)`](https://www.man7.org/linux/man-pages/man2/quotactl.2.html) documents project quotas and hard limits. The application must not assume that it can provision or modify quotas: setup is a privileged deployment operation, while runtime capability checks should be read-only and fail closed.

**Darwin development/qualification path:** require an APFS stage volume with both a quota and a reserve, mounted at the configured stage root; verify its exact volume/mount identity and quota/reserve during startup before enabling writes. Apple documents APFS volume quota as a maximum and reserve as a guaranteed minimum. APFS volumes share their parent container, so a quota/reserve on a volume is not evidence that an ordinary sparse disk-image backing file has physically reserved host-disk blocks. Test against a dedicated physical APFS store or a fixed-size, fully allocated disposable image whose backing allocation and quota can be verified. The existing ownership-enabled APFS fixture is a path-privacy fixture and supplies no stage quota evidence. If the mounted filesystem's APFS identity or quota is unavailable, return unsupported/enforcement-unavailable; do not substitute directory-size accounting.

Apple's [Disk Utility guide](https://support.apple.com/en-kg/guide/disk-utility/dskua9e6a110/mac) describes APFS per-volume quota and reserve. Its description that APFS space is shared within the parent container is why the test fixture must separately prove real backing capacity. Darwin is not the declared hosted production OS; this path is local portability evidence only, not Linux or deployment qualification.

## Accounting, concurrency, and headroom requirements

Keep the software `StagingGate` as early admission and per-account quota accounting, but back it with the kernel-enforced stage cap. Reservation must be global across all accounts/brains and happen before the first write; an OS-cap bypass test must still hit `EDQUOT`/`ENOSPC` when the meter callback is removed. Measured stage/account growth must use allocated blocks/quota usage, including file and directory/inode allocation, not `FileInfo.Size`, payload bytes, manifest lengths, or an average multiplier. Linux quota counters/project usage or a verified platform-specific equivalent are suitable sources; summing `stat.Size` is not.

A single account's multiple brains share the existing product storage allowance. `Physical(account)` must therefore include allocated canonical facts, Git loose objects and packs, the actual index/vector database and SQLite WAL/journal, across all that account's brains. Concurrent distinct-brain writes must serialize their admission against this aggregate and include all outstanding stage ceilings. The maximum accepted mutation fixture must cover the 4,096-byte fact cap, maximum supported plan cardinality/vector width, large Git object fanout/tree rewrite, index/WAL effects, and peak—not just post-cleanup—allocation. Set `MaxMutationStageBytes` above the measured worst case; fail the fixture if a code/config change exceeds it. There is no such measurement or configured production value today.

The kernel stage quota enforces a maximum but does not reserve the data-volume headroom by itself. `ReserveStage`'s `Free()-outstanding-MaxStage >= Headroom` check is only sound if competing local writes are either serialized or included in an OS/accounted reservation. The current backup temp directory shares the data filesystem and is not represented as a gate ticket. Before implementation acceptance, either (a) route every transient consumer such as backup temp/repack/export through a shared operational-capacity reservation that is mutually exclusive with mutation staging, or (b) give those consumers a separate enforced capacity and show the reserved data-volume headroom remains available. Backup must still run when customer quota is exhausted; do not use customer quota to silently block it. Preserve the product's decimal byte quotas and do not change the published plans to fit the current disk.

## Required deterministic qualification

Use real disposable quota-enabled filesystems on each supported OS, with no mount mutation on production hosts. Verify the mount and quota from the test process before running. Tests should demonstrate:

1. A direct write that bypasses `StageMeter` still reaches the kernel limit and fails with `EDQUOT`/`ENOSPC`; the staged area never exceeds its configured hard limit.
2. A one-byte boundary and 50-way distinct-account/brain reservation race preserve global stage budget and `OperatorHeadroomBytes` under concurrent admission.
3. Largest-mutation fixtures measure allocation deltas for source, Git objects/tree fanout, index/vector DB and WAL/journal; assert `MaxMutationStageBytes` covers the measured high-water on the supported runtime.
4. A staged write that exceeds the per-account physical quota is refused before canonical ref publication; no acknowledged source is removed, including at the exact one-byte boundary.
5. Backup/full snapshot temp and operational writes are bounded, do not race the stage budget, and remain available at customer-quota exhaustion.
6. Crash/restart at each stage/publish/ledger boundary preserves accounting: unknown or ledger-committed staging data is never discarded by age alone, and only proven-unpublished/discarded stage bytes are reclaimed.
7. Missing quota, unsupported filesystem, wrong mount, lost quota state, inadequate backing free space, or unavailable physical counter is a startup/reservation error. No graceful accounting-only fallback.

Existing reference `RunStagingSuite` and StageMeter tests prove the in-memory semantics only; they cannot satisfy these OS-level cases. T23.44 multi-package qualification must follow the shared build lease and load limit.

The key ambiguity is not whether ext4/APFS can enforce a filesystem/quota cap; both provide mechanisms. It is how the exact set of canonical and derived writes is confined to the bounded stage while keeping current cross-brain/account semantics, postcanonical indexing, backup capacity, and crash-safe publication. The safest immediate step is a scoped design/ownership contract for that boundary; a source-only quota probe or mounted test fixture cannot complete T23.44.
