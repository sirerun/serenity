## Reviewed implementation details

The new callback placement is sound for the local queue path. `MemoryFact.RememberContext` submits one `Job.Render` at `internal/writer/memoryfact.go:94-100`; `rememberLocked` completes projection loading, keyed duplicate/cancellation checks, and ID allocation before calling `BeforeCommit` at lines 120-155, immediately before `WriteMemoryFactBy` at line 172. The callback therefore occurs after handler validation and the writer's deterministic no-write decisions. `Queue.Submit` waits for the drain goroutine's reply (`internal/writer/queue.go:134-150`), so the callback's write to `operationEntered` happens-before the gateway reads it after `Handler` returns. The false case releases the reservation; if finalization itself fails, the joined error is surfaced. The callback's successful `EnterCanonical` is the transition that marks the operation as entered; a later unknown result remains held for recovery rather than being released.

The private ledger ID is carried as a separate durable field: `internal/writer/memoryfact.go:157-169` stores `CanonicalOperationID: operation.ID`, distinct from the client `OperationKey`. Client JSON cannot set this trusted field: it is absent from `rememberRequest` (`internal/server/memory/remember.go:17-25`), and the regression `TestRememberIgnoresClientCanonicalOperationID` checks the durable payload.

The placement does not complete T23.44's broader cross-process fencing/reconciliation contract. A process-local queue reply establishes memory ordering; it does not itself establish the distributed `BrainFence` required by `internal/hosted/contracts/operations.go:381-404`. The service wiring gap above leaves the contract checker/fence unused for automatic recovery in this candidate.
