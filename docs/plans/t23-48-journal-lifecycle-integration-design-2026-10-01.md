# T23.48 journal dependency and lifecycle integration design — 2026-10-01

Reviewed against current main `230234c969058807236af76d91da0967357a37cd`; design only. The stale canonical `R-hosted-lifecycle` ref has since been resolved by exact-SHA CAS and is absent at review time. PR #273 and its historical source remain preserved. This receipt does not claim T23.48 acceptance, grant production credentials, or qualify AWS or cross-host recovery.

## Current seams and unsafe gaps

- `internal/hosted/service/service.go:257` assembles Gateway, runs local `recoverDeletions`, and only then installs the HTTP handler. That ordering is useful, but current recovery queries only SQLite `accounts.status='deleting'`; it does not inspect the external journal. Any journal read, validation, credential, or recovery failure must stop assembly before handler publication and close opened resources.
- `internal/hosted/service/deletion.go:14` freezes the account and calls billing closure before `Gateway.DeleteAccount`. The Gateway then locks `Maintenance` only around each nested `DeleteBrain` call (`internal/hosted/gateway/lifecycle.go:80,115`), leaving provider work and the gaps between brains outside one gate. The account-wide operation also calls functions that could recursively acquire the same `RWMutex`; once a writer is waiting, that can deadlock.
- `Gateway.Export` and inventory currently do not take the maintenance read lock. An exclusive account-deletion window therefore would not fence every path that reads or flushes the same brain unless those paths join the lock protocol.
- `Service.Backup` currently invokes legacy `backup.Create` and emits no v2 manifest or journal watermark (`internal/hosted/service/service.go:358`). Frozen `contracts.ManifestV2` already carries `JournalWatermark`; the task49 backup writer/caller is still required to capture and serialize it.
- The journal package is present, but an S3 adapter using the AWS default credential chain is not production wiring: the hosted app denies IMDS. Do not use that adapter until T23.54 supplies the dedicated retained bucket and least-privilege policy plus a scoped credential source, and T23.50 establishes authoritative generation/adoption and old-writer fencing. A configured generation number alone is not adoption proof.

## Minimal safe code slice

1. **Inject the interface; never invent a fallback.** Add a narrow service assembly option carrying `contracts.DeletionJournal` and pass the same instance into Gateway. Production construction must obtain it from an explicitly configured, scoped factory supplied by the infrastructure/credential owner; do not create an implicit filesystem journal or SDK default-chain client. A missing dependency makes hosted deletion unavailable with a typed error before provider, database, pool, Git, or index mutation. If startup has pending local deletion state or must perform journal replay and cannot, fail assembly before handler publication. Test assembly supplies `deletion.NewFilesystemJournal` explicitly. Keep any no-journal assembly helper limited to tests with no deletion/recovery request; deletion tests opt into the explicit fake.
2. **Use one non-recursive exclusive maintenance boundary for account deletion.** Introduce a Gateway-scoped exclusive maintenance callback/scope that acquires `Maintenance.Lock` once and exposes only operations that assume the lock is already held. `Service.DeleteAccount` performs the complete sequence inside it: append durable account intent; freeze account in SQLite; call provider closure and require a definite closed result; append/perform each brain intent and purge; anonymize/revoke account data; then append terminal purge outcome. Regular `Gateway.DeleteBrain`, export, inventory and MCP call paths take the read side. Account deletion and startup replay use lock-assuming internal methods rather than calling public wrappers and recursively reacquiring the RWMutex. Retain the current rule that uncertain provider closure leaves the account deleting/restricted and all brain bytes intact.
3. **Journal every irreversible unit and propagate uncertainty.** Append an opaque account `requested` entry before provider closure or purge, and append each opaque brain `requested` entry before dropping it or revoking/erasing its state. Record `purged` only after the full applicable erasure has completed: working-tree bytes, Git history and derived FTS/vector rows, plus credential/session revocation and required provider closure for an account. Append/read/fence errors are hard operation failures; return an error/HTTP failure, never success. Preserve a restricted/pending state after a durable intent followed by provider or journal failure. If final outcome append fails after purge, the request still fails; retry repeats idempotent cleanup and appends the outcome. Do not imply the current Gateway file-removal behavior alone proves all three erasure targets. The journal stores only account/brain opaque IDs, outcome and timestamp.
4. **Replay before handlers, from the backup watermark.** At assembly, validate/read the configured journal and replay every authoritative intent after the restored manifest watermark using idempotent deletion; fail closed on a gap, malformed tail, mismatched hash, absent journal, or uncertain provider close. Existing SQLite `deleting` rows remain a retry input, not a completeness authority. A restored database that predates an account intent must still have that account and its brains purged from the journal entry. Do not advertise recovery readiness from a partial/unsealed read or static generation value: task50's adopted-generation, stopped-old-writer and credential-revocation fence is a separate prerequisite for cross-host restore activation. Production recovery stays blocked until that receipt exists.
5. **Wire the v2 snapshot cut through task49.** While holding the exclusive maintenance scope, flush writers, read the journal watermark before copying any snapshot data, and pass that exact watermark to the task49 v2 backup writer for `ManifestV2.JournalWatermark`. Never synthesize zero. The exclusive lock blocks this process's account/brain delete operations until snapshot completion; cross-host correctness still depends on single-writer fencing. Restore must pass the manifest watermark to `ReadThrough` and replay later entries before serving. Keep the manifest shape and schema frozen; no migration is needed.

The smallest independently testable implementation is the injected journal plus account/brain intent/outcome and whole-operation maintenance scope in Gateway/Service, with a filesystem journal fake. The v2 manifest capture/restore caller is a separate task49 integration commit, and production assembly waits for the T23.50/T23.54 gates rather than claiming them closed.

## Regression plan

- With no injected journal, deletion/recovery returns a typed unavailable error before provider calls or mutations; a broken journal fails startup before handler/readiness publication.
- Inject failure at account intent, brain intent, provider closure, each of the three erasure targets, account finalization and outcome append. Assert no success response, no premature bytes/index/history purge before confirmed billing closure, durable restriction after intent, and idempotent retry without resurrection.
- Block provider closure and one brain purge with channels; prove MCP calls, export, inventory, backup and another destructive lifecycle request cannot enter the protected region until the account operation finishes. Include cancellation, release and no nested-lock deadlock cases.
- Save a v2 snapshot with watermark W, append a later delete intent, restore the older database and prove startup replays that exact subject before serving; corrupt/missing/gapped journal input must fail closed. Verify watermark read precedes every snapshot copy operation and is preserved byte-for-byte in the manifest.
- Keep fixtures local and deterministic. Do not make cloud/provider calls. AWS conditional-write/versioning, IAM, scoped credentials, bucket retention, generation adoption and cross-host stop/revocation remain separately qualified external gates.
