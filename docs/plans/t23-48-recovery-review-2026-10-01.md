## Candidate journal correctness

The candidate’s design is sound in several important respects. `Journal` uses fixed-width generation/sequence object keys, conditional create for sequence ownership, byte-equality readback for ambiguous PUTs, a hash chain, sealed generations, and version-aware S3 listing. It includes paginated listing and reports missing positions as incomplete. The contract suite covers gaps and missing-middle reads, stale writers, history mismatches, seal violations, and generation transitions. The historical S3 qualification exercises conditional create and its bucket-policy enforcement, versioning, a competing writer, a journal round trip/seal, and visibility of a post-seal delete marker. These results qualify the disposable bucket used by that run only; they do not qualify current production IAM/configuration.

There is one adapter correctness gap to fix before port acceptance. In candidate `internal/hosted/deletion/journal.go` (`readGen` around lines 98–104), parsing verifies only JSON, generation, sequence, and predecessor hash. It does not reject an unknown `Kind`, validate an entry’s subject/outcome with `DeletionEntry.Validate`, or require seal records to have the seal shape. `ReadThrough` from a nonzero watermark likewise parses the named object and trusts `Kind` without checking that the object’s embedded generation/sequence match the watermark or that an entry payload is valid. A malformed record can therefore be counted in `To` while omitted from `Entries`, which makes the read look complete while losing a deletion event. Add strict shape validation for every entry/seal, including the resume object, and regression tests for unknown kinds, invalid entries, and coordinate mismatch. A seal alone is only a protocol fence for cooperating writers: the current contract correctly requires stale-writer credentials to be revoked/fenced before a complete journal can authorize activation.

Delete-marker handling is deliberately fail-closed: S3 listing includes both versions and delete markers; a marker-only key is still listed, while `Get` reports no current object body, so `readGen` errors instead of treating the position as absent. The qualification creates a marker after a seal and proves it remains visible and triggers a fence violation. Preserve these semantics, test a missing middle/version case through the S3 adapter seam, and require production bucket versioning plus deny-delete policy. The candidate store maps HTTP 404 in `Get` to “not found”; its callers must continue treating an expected listed key that returns not-found as incomplete, never as the end of the journal.

## Credential and deployment gate

Candidate `NewAWSJournal` uses `config.LoadDefaultConfig`. Current [serenity-hosted.service](../../deploy/hosted/serenity-hosted.service) sets `IPAddressDeny=169.254.169.254` and has no AWS credential environment file. Current [stack.json](../../deploy/hosted/stack.json) grants the instance role backup-bucket and application-secret access, but no dedicated journal bucket permissions. Thus the deployed app cannot obtain the EC2 instance-role credentials through IMDS, and the default chain has no configured alternative. Do not lift the IMDS denial or grant the app the broader host role as a workaround. Before production assembly, name and test an explicitly scoped credential source for the journal; it must support the required list/version-list, read, conditional-write operations for only the retained journal prefix, with delete denied. The current T23.54 stack/IAM work must create that dedicated bucket and runtime configuration. The historical disposable S3 run does not demonstrate that the constrained app service can acquire those credentials.

Preserve current ownership checks, partner-aware paths, account/brain state transitions, and the existing maintenance/account lock order. Do not replace current gateway or service files with PR #273 versions. Deletion must persist its intent before any success response, durably record the completed purge, and leave retryable restricted state on append/provider/purge failure.
3. Inject one configured journal instance into the current production `Service` and `Gateway`, recover before serving requests, and pass that same instance to the T23.49 manifest-v2 backup writer so its watermark comes from the source that recorded live deletions. Do not invent an empty or zero journal adapter. Local filesystem journal remains an explicit development/test fake only; it cannot stand in for production history.
4. Keep current partner-aware billing assembly and call the existing `contracts.BillingCloser` seam for account deletion. The historical `T23.48` result records T23.47 as PARTIAL; a local provider fake or old package test does not qualify live provider closure. Keep T23.47 live closure/contract qualification as a separate gate.
5. Wire the task54 dedicated journal bucket/IAM and the explicit scoped credential source without changing the app’s IMDS denial. Before production use, prove startup/recovery fails closed when credentials, bucket configuration, journal reads or the final seal/fence are unavailable. Complete phase-by-phase crash and snapshot/delete/restore sibling-preservation qualification separately from local S3 adapter tests.
