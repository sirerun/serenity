# Independent review: recovery billing observer contract

Reviewed commit: `85d0c209367ec10792aa34712972395a4170d818` in `/Volumes/BuildOffload/worktrees/serenity-recovery-billing-observer-contract-20261001` (branch `docs/recovery-billing-observer-contract-main343`). Read-only review; no Git refs, repository files, provider accounts, or credentials were changed or accessed.

## Verdict

The proposal has the right fail-closed shape for a read-only point observation: one server-derived account/customer binding, a per-account process lock, a second local-state check, bounded GET-only calls, no SQL writes, and explicit refusal rather than interpreting uncertainty as Free or Eligible. It does not invent old-writer fencing, operator approval, or recovery authority. The separation from `ReconcileCustomer`, `failureEvidence`, and checkout reconciliation is necessary: those current paths write billing state, trust local failure rows, or may issue provider mutations.

The document is a strong implementation brief, but it is not yet a frozen source contract. Several exact behavior choices remain prose-level, and one availability constraint needs a supported operating envelope. Freeze those choices and representative real response shapes before implementation; no production observer or activation claim follows from this review.

## Material decisions still to pin

1. **Status table and terminal behavior.** Freeze a table for every Stripe subscription status under the pinned endpoint version: `active`, `trialing`, `past_due`, `canceled`, `unpaid`, `paused`, `incomplete`, and `incomplete_expired`. The contract currently calls the first six known outcomes in different places, but also says incomplete is ambiguous and uses “expired” without consistently distinguishing `incomplete_expired`. Specify status-to-observation behavior and whether a terminal subscription with an unconfigured historical price can still support an authoritative ineligible result. Current `subscriptionTerminal` recognizes only canceled and incomplete_expired; observer semantics intentionally need a broader explicit mapping.

2. **Event API-version policy.** Freeze an explicit event `api_version` allowlist with one decoder per accepted schema and a policy for empty/null versions. A request `Stripe-Version: 2025-06-30.basil` does not rewrite stored event snapshots. The existing billing service pins direct requests to Basil, but it does not pin the account's event-creation version. Supporting Basil only is safe but can make past-due observations unavailable until matching-version events cover the relevant period; supporting older versions requires actual fixtures and strict decoders for each. Do not accept an unreviewed “compatible” fallback.

3. **Source and error contract.** Pin the exact non-sensitive `Source` tag(s) and stable error classes for local account/status/binding failures, invalid configuration, provider transport/status failures, malformed or unsupported provider data, deadline/cancellation, and exhausted budgets. The frozen contract only says fixed provenance and error; it does not prescribe values. Ensure errors are still the zero observation and cannot expose provider IDs, response bodies, or secrets.

4. **Window, proration, and item-change semantics.** Freeze how applicability is determined when a subscription item or price changes within a billing window, when an event's invoice line is prorated, and when old and new item periods overlap. The proposal's exact subscription-item ID + price + line-level service-period binding is the right conservative basis, but it must state whether a failure for a prior item/window can ever establish grace for the current item. If item identity changes or a line crosses the selected window ambiguously, refusal is safer than moving the failure anchor. Include concrete fixtures for same-window price replacement, quantity-only update, proration line, and renewal-boundary invoice.

5. **Pagination and event ordering.** Stripe's Events list is account-wide and supports either one `type` or a `types` array (up to 20), created bounds, and cursors. Freeze the exact request using `types[]` for the three event kinds, page size, sort reconstruction, and cursor rule. Results should be validated in the provider's returned order, collected only while all pages are complete, then ordered explicitly before interpreting transitions. The current phrase “strictly order by `created`” does not specify whether pagination is newest-first or oldest-first, how equal-second events are handled, or how event IDs break ties; fail on genuinely ambiguous same-second transitions. The event list cannot filter on customer/subscription, so every page can contain unrelated account events.

6. **Retention margin.** The proposal says an item period older than the 30-day Events API window is unprovable. Pin a conservative cutoff with margin (rather than treating the exact 30-day boundary as guaranteed complete), and test boundary ±1 second/day. Do not clip `created[gte]` to the retained suffix.

7. **Response-shape contract.** Pin the exact subscription-list, event-envelope, invoice, and invoice-line fields accepted under each API version, including nullability and allowed unknown fields. The proposal alternates between rejecting “unknown decision-relevant fields” and a general strict decoder. Define which unknown fields are harmless and ignored versus which force refusal. Be especially strict about required `data`, `has_more`, `object`, `livemode`, customer/subscription associations, and line parent/pricing variants. Verify whether invoice lines fetched by GET still prove the association at the payment-failed event time; if the invoice can be changed after that event, event-time evidence must come from the immutable event snapshot or the observer must refuse that case.

## Feasibility against provider and source behavior

The proposed bounds are arithmetically consistent: one subscription request, up to four event pages, four invoice retrieves, and up to four line pages for each invoice is 25 GETs, below the 32-request ceiling. The independent 4 MiB aggregate limit can refuse before those maxima. All provider reads are serial and a 30-second whole-call deadline includes lock wait, so a complete point result is possible for low-volume, recent histories.

The important limitation is that event listing is account-wide, not scoped to the selected customer or subscription. Four pages at 100 events/page cap the scan at 400 events total. An unrelated high-volume Stripe account, or a single subscription with more than four relevant pages / four distinct failed invoices, will fail closed even if its own history is simple. The contract should label the supported usage envelope and treat budget exhaustion as temporary/unsupported evidence, never as non-entitlement. Add a generated fixture with many unrelated events before the relevant failure to prove the implementation refuses rather than silently missing history. Do not call the mechanism “complete” for arbitrary Stripe account volume.

The proposed reliance on the subscription item’s `current_period_start` / `current_period_end` is consistent with Basil’s item-level shape. Stripe’s public docs state that event snapshots retain the API version at event creation, that Events list only reaches back 30 days, and that event listing supports type(s), created filters, and cursors. Stripe describes `customer.subscription.updated` snapshots as subscription changes, and Basil’s subscription item exposes current-period boundaries. These facts support the proposed approach, but do not establish that every production account has all needed historical event versions or enough pagination budget. See [Stripe Events list](https://docs.stripe.com/api/events/list), [Events API overview](https://docs.stripe.com/api/events), [event types](https://docs.stripe.com/api/events/types), [Basil subscription object](https://docs.stripe.com/api/subscriptions/object?api-version=2025-06-30.basil), and [Basil item-period changelog](https://docs.stripe.com/changelog/basil/2025-03-31/deprecate-subscription-current-period-start-and-end).

The reset algorithm is conservative in principle, but its evidentiary premise needs implementation-grade fixtures: `customer.subscription.updated` carries an event-time object snapshot and `previous_attributes`; those snapshots can demonstrate status changes only if the selected API-version decoder proves the subscription, customer, item/price, and service window. An isolated `invoice.payment_succeeded` is correctly not a reset. Any event-time shape without enough fields to bind the transition to the current item must make the observation unknown. Test actual captured/sanitized response fixtures for the selected versions, not only maps synthesized to match the parser.

The no-mutation constraints are aligned with the existing code. `billing.Service.request` accepts a configurable client/base URL, uses a 1 MiB `LimitReader` followed by one JSON decode, and does not enforce EOF or duplicate-key rejection. `listSubscriptions` decodes omitted `data` and `has_more` as nil/false. `failureEvidence` consults and writes `billing_failures`; `reconcileOldCheckoutAttempt` can POST expiry and mutate SQL. The observer should therefore have an isolated transport/parser and read-only SQL queries, as proposed, rather than reusing those helpers. Its account lock is only process-local, which the contract correctly states.

## Concrete pre-implementation acceptance set

Before source work, freeze the seven choices above and retain the existing numeric wrapper bounds. Add a checked-in fixture set from documented Basil response examples or sanitized representative responses for every accepted event version, with deliberate optional/unknown/null variants. Pin tests for the status table, item/price replacement and proration, pagination order/tie behavior, retention safety margin, and the 400-unrelated-event refusal case. Then the source implementation can be reviewed against a finite contract without weakening fail-closed behavior to improve apparent availability.

Provider credentials, account authority, human review, verified snapshot bytes, writer fencing/adoption, and recovery activation remain unavailable inputs. This observer can report bounded billing evidence only; it cannot supply those missing proofs.
