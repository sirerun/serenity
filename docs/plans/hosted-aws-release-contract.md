## Exact signed representation

Manifest is a fixed-field Go struct with JSON fields in this order: version, repository, tag, commit, tree, archive_name, archive_size, archive_sha256, os, arch, go_toolchain, build_recipe_sha256, review_receipt_sha256, test_receipt_sha256, sequence, issued_at, expires_at, policy_id, key_id, algorithm. No optional fields. Version=1, repository=github.com/sirerun/serenity, policy_id=owner-kms-manifest-v1, algorithm=ECDSA_SHA_256. Commit/tree are exactly40 lowercase hex, digest fields64 lowercase hex; archive basename contains only ASCII letters/digits/dot/underscore/hyphen, no dot-only name, slash or backslash. Tag follows current vSEMVER release policy. Archive size positive <=2GiB; sequence positive uint64. OS linux, arch arm64 or amd64, toolchain strict go1.numeric release. Timestamps UTC RFC3339 seconds ending Z, issuance <= current time, expires > current time and issuance, maximum validity7days. Strings and inputs bounded; manifest <=16KiB; signature DER <=256bytes; policy/approval/state <=16KiB each. Verification reads streaming archive with declared-size+1 ceiling and compares exact length and SHA256 before extraction.

Canonical bytes are encoding/json Marshal of validated fixed struct, without trailing newline. Decode rejects unknown fields, duplicate keys at every object, null fields, missing fields (via exact canonical comparison), trailing tokens/JSON/whitespace. Require original manifest bytes exactly equal canonical serialization; semantically equivalent alternative encoding/order is rejected. Decimal sequence/size only canonical numbers. Signature is raw ASN.1 DER ECDSA over SHA256(canonical bytes), produced by KMS Sign MessageType=DIGEST SigningAlgorithm=ECDSA_SHA_256. No JSON signature envelope, embedded trust roots or algorithm negotiation. KMS Sign output key ID/algorithm must match pinned exact ARN/algorithm and signature must pass local offline verification before writing it.

## Independently installed trust and exact deployment approval

Policy is independently installed root-owned regular non-symlink file and includes version, policy_id, repository, exact KMS key ARN, algorithm, DER SPKI base64 and its SHA256 fingerprint, allowed OS/arch. Decode is bounded strict duplicate/unknown/trailing-rejecting and canonical. Parse SPKI with x509 and require ECDSA P256 exactly. Key ARN must match canonical regional/account/key UUID shape, never alias. Recompute fingerprint, never trust artifact-provided key bytes. Key identity is matched against signed manifest. Runtime IAM role has no Sign permission; deployment offline verifier has no AWS calls. Revocation/rotation edits independent policy and requires owner approval; artifact cannot extend policy.

Approval is separate root-controlled canonical file with version, manifest_sha256, tag, commit, archive_sha256, sequence, mode (promote or rollback), previous_state_sha256, issued_at, expires_at. Approver obtains digest independently, not from download automation. Compare every field against verified manifest and immutable previous state. Approval issuance must not be future and expiry must be after issuance and current UTC; max lifetime7days. Rollback permission is exact manifest/sequence/source/archive pinned and cannot be repurposed for arbitrary earlier artifacts. Current state canonical file contains version, highest_sequence, installed_sequence, manifest_sha256. Its digest is exact bytes. Missing state always rejects. Explicit genesis state requires approval previous_state_sha256 equal SHA256 of canonical genesis state {version:1,highest_sequence:0,installed_sequence:0,manifest_sha256:64zeroes}; explicit genesis state must be installed by operator, verifier never treats missing state as genesis. Promote requires manifest sequence > highest_sequence. Rollback requires sequence < installed_sequence and <= highest_sequence, mode rollback, exact current-state digest approval. Same-sequence reinstallation denied. Highest sequence never decreases after rollback.

Production CLI requires effective UID0 and validates policy/approval/state and parent directories: root owner, not group/other writable, no symlink path components, regular files; open descriptor then fstat and compare path identity. Policy and approval are immutable for invocation. State commit uses exclusive sibling flock spanning verification/install staging action; write temp exclusive0600, fsync, atomic rename, fsync directory. A read-only verify command returns verified manifest identity and next state but does not advance monotonic state before installation. Prepare command re-verifies under lock and exclusively creates/fsyncs a sibling pending transaction marker containing version, previous_state_sha256 and manifest_sha256 before installation. Any pending marker causes ordinary verify/prepare to reject. Commit requires exact matching marker and re-verifies all inputs and previous-state digest under lock, atomically writes next state, then removes marker and fsyncs directory. Explicit recover command takes exact manifest pin, repeats signature/archive/policy/approval verification and requires an operator-supplied installed manifest pin; it may complete only the exact pending transaction, including cleanup when state already equals exact intended next state. No automatic pending abort or rollback. Deploy integration must hold the same lock across verify through install and commit; shell opt-in verifier alone authenticates artifact but MUST NOT claim monotonic deployment transaction. Lane supplies verify and commit interface; coordinator owns deploy lock and sequencing integration. Crash before/during/after install leaves durable pending marker and blocks subsequent deployment; explicit exact recovery is mandatory and never auto-lowers state. Lock API: --lock-fd N verifies inherited descriptor is a regular root-controlled sibling state.lock with same dev/inode as safely opened path, then acquires LOCK_EX|LOCK_NB on that descriptor. Without inherited FD command opens and acquires own lock. Deploy holds inherited descriptor across prepare/install/commit; each child validates lock before state access. Root/admin trust boundary explicit; root malicious rollback is not prevented.

## Tool and AWS boundaries

New standalone serenity-release CLI supports canonicalize, sign, verify, prepare, commit and recover. Canonicalize validates structured manifest input and emits canonical bytes without calling AWS. Sign requires explicit region and profile (explicitly loaded selected shared credentials file/profile with static credential provider, never environment/default credential chain or credential_process), explicit policy path and manifest path, output path; creates KMS SDK client with no endpoint override, pinned regional HTTPS endpoint and no environment proxy. It first validates manifest/policy/time, requests KMS Sign digest with exact key ARN, verifies response algorithm/key and real signature locally, writes output exclusively. No GetPublicKey-derived trust bootstrap from sign output. No production invocation during this task. Tests use injected narrow KMS Sign interface with ephemeral ECDSA keys; production constructor uses real AWS SDK. KMS dependency candidate v1.61.4 with corev1.47.1 coordinator-managed. AWS sign command may use authenticated operator profile; workload/broker/service never gets profile or signer API.

Existing verify-release.sh accepts archive bundle tag unchanged under unset or sigstore policy selector. Explicit SERENITY_RELEASE_POLICY=owner-kms-manifest-v1 requires absolute trusted installed verifier path, root-controlled policy/approval/state files and manifest path; bundle argument is raw DER signature. Script invokes installed verifier, never a binary extracted from artifact; command failures stop, unknown selector stops, no retry into Sigstore. Expected CLI tag is independently compared to manifest and approval. Opt-in is source-only until owner-approved root policy is installed. No shell eval, network fetching trust root or extracted archive code execution in verification.
