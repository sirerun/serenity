# T23.44 queue/flush fence design review — 2026-10-01

Read-only review of current hosted remember ordering at `89f07e5`, against the T23.44 commit-fence contract. No implementation or tests were changed by this review.

## Current ordering and gap

1. `Gateway.callBound` holds `Maintenance.RLock`, the account-shard lock, and `Runtime.Mutations` while it calls the tool handler (`internal/hosted/gateway/gateway.go:289–332`). The operation's private `BeforeCommit` callback calls `Operations.EnterCanonical` (`gateway.go:505–516`). It does not currently enter a `BrainFence` commit section.
2. `memory.Handler.remember` validates and calls `MemoryFact.RememberContext` (`internal/server/memory/remember.go:77–97`). `RememberContext` submits one queue job (`internal/writer/memoryfact.go:90–105`). The queue drain takes `runMu`, runs that callback (which loads source projection, calls `BeforeCommit` after validation/dedup and immediately before `WriteMemoryFactBy`), marks source paths touched, then releases `runMu` (`internal/writer/queue.go:134–149`). Thus ledger entry and source mutation are within one queue job, but Git publication is outside that job.
3. After that submit returns, the handler submits a second queue job for `index.RefreshMemoryFactSearch` (`internal/server/memory/remember.go:110–117`). That job can call `Embedder.Embed` (`internal/index/rebuild.go:636–695`) while it holds the same queue `runMu`. A slow embedding provider therefore delays subsequent jobs using this queue.
4. Only after the full handler returns does the gateway call `runtime.Flush()` for successful remember/forget (`gateway.go:519–529`). `Runtime.Flush` delegates to `r.flush()` (`internal/hosted/pool/pool.go:266`); `writer.Flush` acquires `runMu`, takes accumulated touched paths, and performs selective Git commit (`internal/writer/commit.go:28–48`, `90–133`). This creates a gap between ledger entry/source write and Git flush. The source writer's queue lock ends before indexing, while the later flush occurs after provider/index work.

The global `Gateway.mu` in `ServeHTTP` is released before dispatch reaches `callBound` (`gateway.go:179`); there is no evidence that current embedder calls run under that mutex. The broader `Runtime.Mutations` mutex is held across the handler, including the current embedding job. Keep that existing behavior unless separately reviewed; the commit guard proposed below must end before indexing and must not be implemented by extending `Runtime.Mutations` or `Gateway.mu` across provider work.

`commitPaths` stages exact touched paths, filters staged paths to the owned set, and commits only those paths; unrelated staged/unstaged work is preserved. `Flush` restores all taken touched paths if commit fails. Those semantics must remain true for an inline commit. The local queue hook currently runs after each job releases `runMu`, before the submitting caller receives its result; the new path must keep hooks outside queue and commit guards.

## Bounded design

Use two narrowly scoped queue capabilities, both owned by the per-brain runtime:

- Add `Queue.SubmitAndFlush(ctx, root, job)` as a special queue operation. The drain holds `runMu` across the callback, touched-path accounting, and a new private `flushTouchedLocked(ctx, root)` helper. Refactor ordinary `Flush` to take `runMu` and call the same helper; the special path must call the helper directly and must never recursively call `Flush`. `MemoryFact.RememberContext` uses this for the canonical source write, so the first source mutation is committed before `remember.go` starts the separate indexing/embedder job. On commit error, return an error to the handler and restore touched paths exactly as ordinary `Flush` does. Thread `ctx` into the new Git commands so a timed-out request does not wait indefinitely; an uncertain commit result remains pending review for canonical reconciliation. Emit one queue hook result after releasing `runMu`, carrying the combined callback/commit outcome.
- Add a context-aware shared/exclusive commit guard on that queue/runtime. The canonical write operation enters its shared side only after the worker has acquired `runMu` and immediately before `BeforeCommit`/`EnterCanonical`; it releases the shared side only after the callback's source writes and Git flush succeed or fail. The reconciler's `BrainFence.Fence` takes the exclusive side around canonical inspection and the ledger transition. This guard is separate from `runMu`: the latter also covers the later embedding queue job, and reusing it for the checker would make a slow provider stall reconciliation, contrary to `contracts/commitfence.go`.

Preserve the approved order: writer holds `Maintenance(read) → account lock → Runtime.Mutations → queue runMu → shared commit section → short EnterCanonical/Finalize ledger transaction`. Reconciler holds `Maintenance(read) → exclusive commit section → short ledger transaction`; it does not take account lock or `Runtime.Mutations`. Do not hold a SQL transaction across source I/O or Git. Context cancellation while waiting for either commit-guard side must return promptly; an exclusive fence timeout maps to `ErrBrainNotQuiescent` and leaves the reservation unchanged. A queued writer that reaches `EnterCanonical` after the fence released its reservation must be denied before writing its first source byte.

There is an outcome-plumbing detail: today `gateway.callBound` sets `canonicalCommitted` only when its later `runtime.Flush()` succeeds. Once source flush moves into `RememberContext`, the internal operation must communicate that source-commit result to the gateway (for example, a private post-flush callback/result on the trusted canonical context). The subsequent gateway flush still handles index paths, but an index/Git error must not erase evidence that the canonical source was already committed. Keep such signaling private; the client cannot supply the operation ID or commit result.

## Required regression coverage

- Queue unit tests: combined callback+commit holds `runMu` continuously; normal `Flush` and inline flush share touched-path/error-requeue logic; the hook runs after `runMu` and the commit guard release (without changing its existing single-drain/reentrancy contract); unrelated staged and unstaged paths remain unchanged; failed Git commit restores touched paths and does not claim committed outcome.
- Guard tests: cancellation while waiting for the shared side or exclusive fence is bounded; exclusive fence waits for an active source+flush section; a waiting fence prevents new source commit sections from overtaking it; a released reservation causes a stale writer's `EnterCanonical` to fail before any source write.
- Hosted service test with a deliberately blocked fake embedder: canonical source+flush completes first, then embedding blocks; the checker can acquire the exclusive fence and reconcile without waiting for provider completion. Also test source-commit failure versus later index-commit failure so the ledger outcome reflects the canonical source independently of the search cache.

## Separate forget-marker requirement

This design covers the remember source commit only. `MemoryFact.Forget` writes the expiry/cancellation marker, may remove the fact, and can purge the index in its own queue job (`internal/writer/memoryfact.go:202–300`). The marker must also be durably persisted and interpreted by reconciliation after forget, including crashes between marker write, source removal, and Git flush. Do not treat a missing fact alone as proof that an interrupted canonical remember never committed. Track and test forget-marker persistence as a separate correctness item; do not silently assume the remember `SubmitAndFlush` path covers it.

The related evidence at `docs/launch/evidence/T23.44/canonical-operation-identity-2026-10-01.json` already records that queue coverage ends at the source callback and that full fence extent through Git Flush remains open. This report supplies the narrow implementation boundary; it does not claim T23.44 acceptance.
