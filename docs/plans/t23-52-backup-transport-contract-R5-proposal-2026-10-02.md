## Proposed source boundary and dependencies

An eventual source assignment may add a transport module, focused tests, and an owned source receipt; it must also explicitly include the narrow changes in `deploy/hosted/backup_publish.py` and its existing tests required by this contract: `RemoteObject.is_latest`, inventory-first reads, and explicit-version read parameters described below. No other helper behavior is authorized. Do not edit installed scripts/units, caller wiring, the retention helper/runner, deployment configuration, credentials, or destructive authority. Preserve the exact current storage write method: `def put_if_absent(self, key: str, source: BinaryIO, *, length_bytes: int, sha256: str, chunk_bytes: int) -> None`. Keep its name, parameter names, types, keyword-only shape, and return type unchanged.

The definite `ObjectExists` behavior in final-COMPLETE handling was corrected in source commit `68557003d6cbf7b4ec8e01217967793d5743856a`, independently reviewed CLEAR, and the resulting publisher blob is included in current main merge commit `e6dc3f66ee25fe9b9e30b4b3acae6472b812d075`. That prerequisite is fulfilled. Recheck the exact merged source bytes before a later source assignment; this R4 proposal itself remains unapproved and does not authorize implementation. Definite `ObjectExists` never enters the ambiguous completion path.

The new transport module owns a private executor. Do not modify or borrow the retention helper's private runner. Executor ownership is one operation object with one child registry: only that object may reap/terminate its registered children; remove a child from the registry after wait/reap; never signal a PID after removal. No external process runner interface change is authorized. Test executor lifecycle independently with injected process factories. Apply one absolute operation deadline to each child and every read/write; each child gets `min(30 minutes, exact remaining operation time)`, never a refreshed timeout. Every subsequent pass consumes the same 24-hour budget. For bounded GET output, use an operation-owned single-threaded launcher that sets `RLIMIT_FSIZE` to 134,217,728 bytes, then `execve`s the pinned CLI in the same PID; do not use a shell or detached descendant. An equivalent kernel-enforced per-file quota is acceptable only if tested against the child actually writing the file. The publisher opens a unique nonexistent path and rejects any child failure/limit signal before consuming output.

The narrow publisher handshake is required: add `RemoteObject.is_latest: bool`; change reads to `read_bytes(key, *, version_id, max_bytes)` and `read_to(key, destination, *, version_id, max_bytes, chunk_bytes)`; obtain and validate complete inventory before reading COMPLETE, manifest, or artifacts; pass the selected explicit ID to every GET. Select exactly one latest ordinary version per required key at the completed inventory's observation point. No hidden cache or call-order-dependent binding.

A later same-key version created after inventory does not change the version ID requested by a pinned GET. However, explicit version reads do not prove that the selected version remains latest. Publisher and downloader must perform a final complete versions-plus-delete-markers inventory after all full-body/hash passes and verify the full identity set `(key, version_id, delete_marker)` against the initial inventory plus only the exact versions this publication created (or the unchanged initial inventory for a download); verify selected/current version IDs, exact key set, and expected full-object lengths and SHA-256 values before returning success or a qualified receipt. Any newer same-key version, marker, missing key, extra key, changed ID, or checksum mismatch fails closed. This final list is an observation, not an atomic multi-key snapshot; the exclusive writer and mutation gates below are mandatory across the entire operation to make those observations meaningful.

The helper's definite final-COMPLETE `ObjectExists` exception is not an ambiguous lost response and must never enter exact-readback reconciliation. Only an uncertain post-transmission transport outcome may reach that path, and only exact full-object byte and digest readback can reconcile it. The coordinator-owned corrected source merge and independent test review are complete; confirm the exact merged bytes at the eventual assignment boundary. The R4 proposal itself still awaits coordinator freeze and a separate explicit source assignment.

## Remote configuration and preflight

One configured general-purpose S3 bucket, region, and expected 12-digit account owner only. Require an absolute caller-pinned AWS CLI executable and a caller-pinned accepted version/build identity; no CLI discovery, executable search, ambient AWS profile/config, endpoint override, or directory bucket. Parse and validate all config and hard ceilings before child creation. Use argv arrays without a shell. Credentials arrive only as an explicit short-lived allowlisted environment input; never discover ambient credentials or serialize secrets into argv, logs, exceptions, or test output. Use an operation-owned sealed minimal CLI config/credentials file with only the approved region and explicit short-lived credentials; reject `credential_process`, SSO, web-identity discovery, credential plugins/providers, command aliases, endpoint overrides (including environment-configured endpoint URLs), and unknown config fields. Pass exact `AWS_CONFIG_FILE`/`AWS_SHARED_CREDENTIALS_FILE` paths to these minimal files and reject profile selection. Disable pagers/prompts and CLI config discovery; set one attempt for every request (no CLI or transport retry of writes). Each request carries expected-bucket-owner where supported. Fake-process tests establish argv/environment construction only; they do not establish production trust, credential provenance, or executable integrity.

Before inventory or any write in a publication operation, call `GetBucketVersioning` with the configured bucket and expected owner. Require status exactly `Enabled`; absent status, `Suspended`, malformed/oversized response, owner mismatch, or failure refuses the operation with zero object writes. Repeat this preflight on each new publication invocation; do not cache across invocations. Also require exact prefix validation and configured region. The application cannot prove bucket policy or exclude an administrator race from this call; those remain deployment gates below.

## Fixed hard bounds

Configuration may choose smaller values, but cannot raise these source ceilings:

- Total snapshot bytes: 500,000,000,000; object count 1,003; per-object bytes 500,000,000,000.
- Version inventory: honor the existing helper request `max_objects=1,003` exactly, counting all versions and delete markers together; at most two pages per snapshot prefix at `--max-keys 1000`. Exceeding 1,003 combined entries or two pages fails closed without returning partial inventory. Every version and delete marker counts. The helper ceiling is the source of truth, not a transport-specific larger history limit.
- ListObjectVersions JSON/stdout per child: 16 MiB; all other stdout per child: 64 KiB; stderr per child: 256 KiB. With at most seven inventory passes and two pages each, plus 24,576 bounded children, the worst theoretical stdout budget is below 1.72 GiB; set the aggregate output ceiling to 2 GiB stdout and 64 MiB stderr. Drain incrementally and reject at the boundary; never buffer aggregate output in memory.
- Multipart part size: fixed 256 MiB except final part (which may be smaller); maximum 1,863 parts for the 500 GB ceiling, well below S3's 10,000-part limit. Validate calculated count before create-multipart-upload.
- Child wall time: at most 30 minutes and never later than the operation's remaining 24-hour deadline; operation wall time: 24 hours; process invocations: 24,576; concurrent children: one. Propagate one absolute operation deadline into every child launch and I/O wait; a child receives `min(30 minutes, operation_deadline - now)` and cannot start with zero remaining time. No child gets a fresh allowance after a prior wait or retry. No retries. Deadline cancellation has a maximum 60-second cleanup/reap allowance; cleanup timeout/unconfirmed reap is an operation failure, never success/receipt. On any other ceiling breach, fail closed and clean up only invocation-owned resources.
- Scratch and disk ceilings: upload spool at most one object, capped at 500,000,000,000 bytes; GET range scratch exactly one file, capped at 134,217,728 bytes; publisher remote-verification tree at most 500,016,781,312 bytes (500,000,000,000 artifact bytes + 16,777,216 manifest + 4,096 COMPLETE); download staging at the same bound. All files are mode 0600 and newly created with exclusive/no-follow semantics in caller-designated private directories. During maximum-size publish verification, the caller's 500,000,000,000-byte local input + verification tree + one GET range file may occupy up to 1,000,150,999,040 bytes, excluding filesystem metadata and preexisting caller files; reserve at least this much on the private volume or fail before transfer. During upload spool peak, local input plus spool is at most 1,000,000,000,000 bytes. GET range output is hard-capped while the CLI child writes, not just checked afterward, as specified below. Check free space before transfer and enforce limits while writing.
- Stream buffers: 1 MiB maximum; `read_to` writes chunks no larger than the requested chunk ceiling. JSON and part-completion structures are bounded by the object/page/part limits above.

All fields must be explicit, type-checked, finite positive integers (no bool-as-int), and cross-validated before launching the CLI. Tests must prove ceilings at boundary and one over.

## Existing helper readback paths and required aggregate budget

The merged publisher is not a single-read verifier. In `publish_snapshot`, `_verify_remote_payload` downloads and hashes every artifact and reads the remote manifest before writing COMPLETE (full artifact pass 1). After the commit write, `_verify_remote_completed` reads manifest/COMPLETE and downloads/hashes every artifact again (pass 2). If the final COMPLETE write has an ambiguous outcome, exact small COMPLETE readback is followed by `_verify_remote_completed` inside reconciliation, then the unconditional `_verify_remote_completed` runs too: three full artifact passes total (pass 3). The merged definite `ObjectExists` branch rethrows immediately; it cannot use the ambiguous path. `download_snapshot` verifies one full artifact pass. These are direct paths in merged `backup_publish.py`, not an assumption about a future caller.

Budget the worst ambiguous publish path: up to three full remote artifact passes at 500,000,000,000 artifact bytes each = 1,500,000,000,000 artifact bytes downloaded. Count control data conservatively too: at most three 16,777,216-byte manifests and three 4,096-byte COMPLETE records, giving a maximum full-byte proof budget of 1,500,050,343,936 bytes. Normal publish is at most two such passes; a standalone download is at most one. These are hard transfer ceilings for one operation, not throughput guarantees. Any unexpectedly repeated helper read, extra version, or byte above the budget fails closed.

Use 134,217,728-byte (128 MiB) GET ranges, one output file per request. For a 500,000,000,000-byte aggregate across at most 1,001 artifacts, conservatively budget `ceil(total / range_size) + object_count = 4,727` range GETs per full pass, plus at most 1,001 HEAD requests to bind each object's declared length and exact version. Thus three full passes require no more than 17,184 artifact HEAD+GET requests. With up to 3,163 write requests by conservative independent upper bounds (1,001 single PUTs + 1,962 multipart parts + 198 create/complete calls + manifest and COMPLETE writes), at most 14 inventory pages, one mandatory versioning preflight, one CLI-version check, and bounded control-object HEAD/GET calls, the worst ambiguous-publish path stays below 20,500 child invocations. Set the hard total invocation ceiling to 24,576. This arithmetic is a conservative design budget only; any helper-call shape change must recompute it before source review.

## Full version inventory and reads

Use `s3api list-object-versions` for the exact snapshot prefix, `--encoding-type url`, `--max-keys 1000`, no delimiter, expected owner, and manual pagination without CLI auto-pagination. Decode keys and both continuation markers exactly once with strict percent/UTF-8 validation. If truncated, both markers are required, valid, and strictly advancing. Require bounded valid JSON, boolean `IsTruncated`, typed Versions/DeleteMarkers arrays, typed `IsLatest`, nonempty non-`null` opaque version IDs, no duplicate `(key, versionId)` identity, no out-of-prefix key, no common prefixes, and no malformed/unknown pagination state. Return all pages or an error, never partial inventory. Count markers and all historical versions. Require no out-of-band writer, deletion, versioning, lifecycle, or administrative mutation during the entire inventory-to-final-verification interval. The API provides paginated observations, not an atomic point-in-time multi-key snapshot.

After inventory, each required read must select exactly one ordinary `IsLatest=true` version for that exact key. For every selected version, first call `head-object` with explicit `--version-id` and expected owner; require `type(ContentLength) is int` and `0 < ContentLength <= max_bytes` and typed `VersionId` equal to the selected ID. The API passes a byte ceiling, not an unknown exact record length. For COMPLETE and manifest bootstrap reads, require a positive `ContentLength` within their configured maxima (the current record formats are nonempty); fetch that exact HEAD-declared body using explicit-version `get-object --range bytes=start-end` requests, each at most 134,217,728 bytes, and require body byte count to equal HEAD `ContentLength`. Validate each response's typed `ContentRange`, `ContentLength`, and `VersionId` against the exact requested span, HEAD total length, and selected ID before consuming the chunk. For download, only after bounded COMPLETE bytes are assembled validate its exact record structure and bound manifest digest; then bounded-read manifest, verify its digest against COMPLETE, and parse it. For publisher checks, compare the bounded-read manifest/COMPLETE bytes to the helper's expected canonical bytes. Artifacts use manifest-bound `max_bytes` ceilings; require HEAD and assembled response not to exceed the ceiling and match each other exactly, then let the helper's existing length/hash verifier enforce exact manifest length and digest. The current manifest-v2 contract rejects zero-length artifacts, so all current COMPLETE, manifest, and artifact objects require positive ContentLength; no zero-length GET path is accepted.

The AWS CLI writes each range body to a unique private outfile whose child process has an OS-enforced file-size limit of exactly 134,217,728 bytes before exec (or a demonstrated equivalent hard quota); if a response exceeds that cap, the request fails and no bytes from it are accepted. Never treat an after-write `stat` check alone as the disk bound. Stream validated chunks to the publisher destination in chunks no larger than `chunk_bytes`, hash/count across the complete object, then securely remove each chunk before the next request. A key gaining a newer version after the initial inventory still gets the explicitly selected old ID; after all reads, a final full inventory comparison must detect that the selected ID is no longer latest and refuse success. Hash validation remains mandatory. Downloaded content remains bytes in private staging; the adapter cannot activate, install, or qualify a live recovery.

## Writes and version-safe publication boundary

For every destination prefix, complete the entire bounded versions+delete-markers inventory first. Any prior version or delete marker for a destination key blocks publication. Never infer absent history from `ListObjectsV2` or a current-object GET.

For objects no larger than 5,000,000,000 bytes, use file-backed `put-object` with `If-None-Match: *` and expected owner. Larger objects use CreateMultipartUpload, bounded file-backed UploadPart calls, then CompleteMultipartUpload with `If-None-Match: *` and expected owner. Keep upload ID and exact part ETags in the operation registry, in order; ETag is not SHA-256. Abort only the upload ID created by this operation on definite failures. Abort failure, spool cleanup failure, or unresolved process ownership means no successful result/receipt. Require deployed lifecycle expiry for incomplete multipart uploads; the versions API does not enumerate open uploads.

Before network write, copy source bytes incrementally to a new 0600 private regular file, counting and hashing during copy. Enforce declared length, object/total ceiling, source stability, and scratch ceiling as data arrives. Reject symlink/non-directory scratch, collisions, owner/mode violations, changed source identity/size/mtime, early EOF, extra bytes, digest mismatch, disk full, timeout, and cleanup failure before reporting success. Do not send large objects through captured stdin or memory buffers.

`If-None-Match: *` is only a current-version precondition. In a versioned bucket, it can succeed if current version is a delete marker; it does not assert all-history absence. Safe application publication requires versioning status Enabled and the inventory refusal above, plus deployment-enforced conditional writes and an exclusive writer/mutation gate. The deployed role/policy must deny runtime DeleteObject, DeleteObjectVersion, versioning suspension, and competing lifecycle/admin changes that could add a marker or remove a current version between inventory and final write. The gate must serialize this publisher's writers and exclude all other writes/deletes/versioning changes for the snapshot prefix throughout publication/download and final verification. It must also verify that no active lifecycle expiration rule or noncurrent-version expiration rule can create delete markers or remove snapshot history; denying future lifecycle API changes with IAM does not disable existing configured rules. Conditional final writes decide a concurrent absent-key race only between cooperating writers inside the gate. If deployment cannot prove the gate and mutation denies, qualify only conditional-current-version behavior, never “atomic all-history absent.” Do not repair bucket state automatically.

A definite 412/`ObjectExists` is an occupied key and stops. A 409 or other definite response is failure; timeout, connection loss, malformed response, or child uncertainty after request transmission is ambiguous and is never blindly retried. Only the independently corrected final-COMPLETE helper may reconcile an ambiguous final write by reading the exact full object back and matching exact expected length and SHA-256. It must not reconcile the definite `ObjectExists` exception.
