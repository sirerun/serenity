Lambda validates requestContext API ID, account ID, stage, domain and exact method/path against deployment binding, and identity.userArn/caller/accessKey against enrollment. This is a trusted-host software boundary, not hardware attestation. Broker enrollment maps AWS role and unique instance to exact deployment/namespace/build digest; owner enrollment is a separate privileged AWS principal and route. User-controlled headers, request body, CLI flags, environment build labels, or direct function invocations cannot mint caller identity. Runtime principal has invoke only; Lambda gateway alone has DynamoDB transactional writes and dedicated immutable S3 witness writes. Owner/admin/breakglass/policy mutators remain explicit trusted authority, enumerated in deployment inventory and activation receipt. IAM revocation is not the write fence: each write CAS-tests the durable ACTIVE state, epoch, lease and head in the same transaction as create-only object and durable receipt.

## Durable data and bounds

One DynamoDB partition per exact owner-enrolled deployment+namespace identity. META stores monotonic revision, state (ENROLLED/PREPARING/ACTIVE/CLOSED), epoch, head JournalPosition, generation seal state, enrolled release policy, reservation/lease identity and expiry, last witnessed sequence/hash, and at most one pending witness. Immutable items: OBJ#canonical-key (canonical stored bytes <=64KiB), ISS#writerID (epoch/generation/build/principal/attempt), OP#authority-operation-ID (request digest and durable result), ATT#random256 (challenge nonce digest, expiry, consumption), CUT#random256 (exact position/witness anchor). One namespace is one authority lineage; table ARN plus authority lineage ID are pinned in enrollment. No DynamoDB TTL removes history, operations, cuts, issuance or authority state. Retention requires a separate reviewed protocol.

Every external body <=96KiB before decode, strict JSON unknown-field rejection, canonical identifiers <=256 bytes, random IDs fixed 64 lowercase hex. One JSON object only. Prepared reader supports both global deletion-journal/ listing and exact generation prefix: complete namespace scan catches malformed or impossible higher-generation keys. Cut reader filters only later canonical positions under the trusted cut boundary; malformed keys are errors, never silently filtered. DynamoDB object payload <=64KiB; reads <=64KiB/object, List 1..256 keys, no arbitrary prefix outside deletion-journal/. Observation existing limits remain 10000 generations/100000 objects/64MiB total. State never returns secret credentials. Receipt request digest binds action, enrollment, full payload and principal; operation reuse with different digest is conflict.

## State machine and transaction rules

Owner Enroll conditionally creates META ENROLLED with explicit namespace lineage, runtime principal and approved measured builds. Owner GenesisPermit is an immutable create-only item bound to lineage, generation 1, issuer, audience, expiry, nonce and authority-assigned operation ID. Prepare consumes the single-use permit atomically only for never-issued namespace; empty object listing is never genesis proof. Successor Prepare allocates epoch and writer ID itself, conditionally revokes previous ACTIVE epoch, holds PREPARING until Activate or exact Close; no concurrent attempt steals PREPARING or renews old epoch. Lease expiry always denies writes; expiry does not authorize enrollment/genesis/reset.

Challenge issues authority-generated random attempt+nonce with short expiry; Prepare atomically consumes exactly that attempt once and binds principal, kernel-measured build/instance and full request digest. Exact replay resolves existing operation; a nonce replay with another operation/payload is rejected. Challenges are not startup authority until consumed. Prepare durable result contains reservation ID, writer ID, epoch, exact JournalPosition and bounded reader capability. Exact prior epoch remains fenced during observation. Renewing lease, if implemented, is a CAS on exact active lease and policy; never silently reacquire.

Read capability is bound to principal, namespace, epoch/reservation or cut ID, expiry and immutable head. Get/List reject anything beyond captured head and all noncanonical keys. Strongly consistent Query/Get; pages always carry exact same position/anchor. Reservation validity is checked on every read and publication admission. Immutable old objects allow cut readers to continue while new writes append; cut readers cannot see later positions.

Activate independently re-observes canonical history through the reserved reader and reconciles every observed WriterUse with immutable ISS records and exact prior issued generation. Caller observation hash is only a comparison input. Activation and service readiness recheck exact effective TIP and position; preparation may replace writer within the same active generation, with issuance reconciling each historical WriterUse. Activation CAS-tests unchanged PREPARING revision, reservation, expiry and head, then creates immutable new writer issuance and ACTIVE lease. Genesis writer and successor allocation identity are authority assigned. Existing deletion.NewWriterJournal enforces structural position, not authority. No forced generation advance: active generation stays current unless canonical seal already commits successor generation position.

Append accepts lease ID, canonical key and exact canonical body; operation ID is stable SHA256(domain + lease + key + body). Runtime Append permits entry kind only; seal is exclusively an owner-authenticated recovery route. Gateway strict-decodes JournalObject and requires re-encode equality, matching WriterID, valid kind/subject/outcome/time, exact expected next key/prev hash and generation. Transaction updates META conditioned on exact ACTIVE lease/epoch/unexpired policy/revision/head/no pending witness; Put OBJ condition attribute_not_exists; Put OP condition attribute_not_exists. Seal atomically moves active position to next generation with predecessor seal and authority-generated successor allocation. Transaction conflict never means successful append. Durable identical OP resolves lost response; mismatched OP rejects. Existing object with matching bytes is found only after confirming witness durability; different bytes is conflict. All reads after ambiguous errors are strong and context bounded; uncertainty returns retryable unknown without success.

Close/Revoke checks exact lease/reservation and operation digest, atomically sets CLOSED and receipt. Retries resolve exact OP; cannot revoke successor. Current checks ACTIVE exact epoch/lease, unexpired enrollment/build policy, no unresolved witness; returns exact head and epoch. Service admission checks Current before publication/readiness and after replay; mutation protection remains transaction-local so stale readiness cannot create a write race.

## Independent witness and disaster restore

Every state mutation (including enrollment, prepare, activate, append and revoke) commits pendingWitness containing canonical state transition, exact object bytes when present, operation digest/result and previous witness SHA256. This same DynamoDB transaction is the serialization point; no further state mutation, append acknowledgment, activation/publication, or cut succeeds until the exact witness has been conditionally PUT to a dedicated S3 prefix and read back equal. Witness keys are sequence/digest pairs, lineage-bound; IfNoneMatch is enforced and overwrite/delete/version-delete/lifecycle mutation denied to operational principals. Gateway confirms persisted witness then CAS-acknowledges only identical pending digest and revision. Crash at any phase resumes from durable pending data; lost witness response uses bounded readback. No delete side effect follows an unwitnessed append.

Witness keys contain sequence plus SHA256 of exact witness bytes. TIP references exact key/hash and each witness exact predecessor key/hash. Complete recovery traverses the TIP ancestor chain backwards with bounded depth/bytes and verifies forwards to enrolled genesis; limits fail closed. No listing inference. A witness persisted before failed TIP CAS is unreachable, unacknowledged and has no permitted side effects; preserve it, exclude it from authenticated history, never delete/adopt it automatically. Distinct digests avoid sequence collision. Rebinding table preserves previous TIP ancestor, therefore every acknowledged deletion. Pending intent lost with DDB is recoverable only if already in TIP ancestry; otherwise unacknowledged tail. Old PITR is never automatic admission.

Cut is a witnessed serialized authority operation using the same pending/TIP protocol. Cut requires Current and no pending witness; it creates immutable CUT tied to exact head/witness anchor, lease/epoch, authority lineage, snapshot attempt and expiry. Subsequent journal append does not change cut reads. A strict versioned cut sidecar cryptographically binds snapshot manifest SHA256 to this authority cut and complete observation; existing manifest v2 stays unchanged, and no unsealed head is falsely marked sealed. BeginCut captures the durable position before snapshot data copy. FinalizeCut(cutID, exactManifestSHA256, operationID) creates a second immutable witnessed authority record binding the cut and manifest bytes. Sidecar references that record, never substitutes for it. Backup destination publication follows successful FinalizeCut/readback and sidecar fsync. Ambiguous finalize retries identical operation/body; restore fetches authenticated authority record and compares exact manifest hash. Restore authorizes a fresh table lineage only through owner route, validates the complete latest witness chain and snapshot cut ancestry, reconstructs every later deletion, then starts ordinary fenced preparation. Runtime cannot request enrollment or accept an arbitrary cut. Recovery approval and deletion-safe replay remain independent existing gates.

## Cross-table fencing witness tip

Bootstrap is an owner-only explicit enrollment+genesis operation which conditionally creates the initial TIP; absent TIP never authorizes runtime bootstrap. The independent S3 witness prefix additionally holds one mutable, versioned TIP object with exact lineage, active table ARN, authority epoch, witness sequence/hash. Each state transition reads the exact old TIP and validates its table/lineage/epoch against enrolled META before its DDB intent transaction. After immutable witness PUT/readback, it advances TIP with IfMatch of that exact old ETag. A successful TIP CAS followed by equal readback is mandatory before DDB witness-ack and success. A CAS conflict is never retried using an arbitrary newer ETag: only exact identical result can resolve ambiguity; otherwise transition remains unresolved and runtime fails closed. Concurrent calls resolving the same pending witness may observe already-identical TIP and finish the exact same operation. TIP cannot point at a witness not already immutable and readback-verified.

Owner restore/migration first publishes immutable complete-history successor witness with source tip and new table identity, then CAS-rebinds TIP to that table/epoch, and only then enrolls/restores the new table via owner route. Old gateway can still write pending intents to its retired DDB table, but cannot advance TIP or acknowledge append/activation; old leases cannot cause deletion side effects. All control transitions and Current verify TIP identity; Current additionally requires local witnessed anchor to match TIP. TIP changes are authority operations, never runtime request fields or untrusted latest-head hints. Owner role alone rebinds table identity. Runtime gateway role may advance ordinary TIP within exact enrolled lineage/table only; code and IAM principal inventory together enforce this. IAM cannot inspect JSON TIP body, so compromised trusted gateway code is explicitly inside the authority boundary. Tip updates are mutable control state, not immutable journal objects; no claim that conditional-create alone protects TIP.

Any failed or unknown TIP read/CAS keeps pending witness unresolved. Old-table rollback meets a newer TIP and fails closed. Restore compares complete witness chain with the exact independently read TIP anchor, rejects ancestor holes, truncated chain or divergence; unattached immutable candidates are preserved outside authoritative history, and never accepts a caller-provided anchor. Witness state/tip cannot be mutated by runtime or snapshot writer roles. Resource/policy administrators remain owner-controlled trusted mutation paths and require inventory at activation.
