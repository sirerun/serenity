# T24.28 macOS keychain readiness and legacy blocker

Date: 2026-10-02. These are disposable-keychain probes on macOS. All items were created in unique temporary keychains, selected explicitly for add and search, and removed afterward. Process-wide keychain interaction was disabled and verified before item calls. No default keychain, pre-existing item, or real secret was queried or changed. No Serenity repository source was edited.

## Integration choices for review

Keep the existing public secrets API and legacy credential bytes unchanged. The runtime evidence supports creating newly written items with a creator-restricted ACL, then reading/updating those items without UI. It does not support promising that already-existing security-CLI/go-keyring entries can be transparently migrated under the same no-UI contract.

Recommended boundary for source design: make native restricted creation the path for new writes, while treating legacy retrieval/migration as an explicit compatibility decision before wiring it. Options for that decision are:

1. An explicit migration/operator handoff for existing entries. A migration can be attempted only after a supported way to make the old item readable and to complete ACL changes is designed and separately tested. Current evidence says the read is denied and the owner setter stalls.
2. A carefully scoped legacy-format compatibility path that continues to use the existing implementation for old entries. This preserves access to existing credentials and bytes, but necessarily preserves the old item's access policy and cannot claim the new restricted ACL for those entries.
3. An opt-in alternate backend or migration command while the current API remains source-compatible. This still needs a defined behavior when an old read returns `errSecAuthFailed`; automatic UI prompting or silently resetting/replacing credentials is not supported by these probes.

Do not silently reinterpret a denied legacy read as “not found,” overwrite it with a new secret, or fall through to a weaker store. No production patch should proceed until the legacy-compatibility boundary and its user-visible failure behavior are selected and reviewed.

## Cleanup and limitations

Both timed-out legacy fixtures and the successful restricted fixture were removed by exact recorded keychain path and unique temporary-directory identity. The successful green control's fixture was likewise removed. This evidence is limited to disposable file-keychain behavior on this host and to the tested Go runtime/codesign identities; it does not establish every macOS release or login-keychain configuration.
