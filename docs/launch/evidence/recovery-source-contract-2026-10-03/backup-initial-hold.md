# Independent review: verified snapshot lease source contract

**Verdict: HOLD** for source implementation. Reviewed proposed source document at exact author head `ac2367f7a033428217f68a0f1793fe40887716e2` in the isolated reviewer clone. This is a contract review only; no source edits, builds/tests, provider calls, or acceptance claims were made.

The core direction is sound: retain the exact verified copies, expose only a bounded historical projection, keep billing/provider eligibility separate, and make physical quota a separate gate. The following contract seams need resolution before backup implementation can be reviewed against a callable, restartable API.

## Blocking seams

1. **`Pin` cannot return the durable pin record the consumer must persist.** In `docs/plans/verified-snapshot-lease-proposed-source-contract-2026-10-03.md`, the proposed method returns `PinnedSnapshotRef` (`:39`), while only the distinct `SnapshotPinRef` declares `ID`, `ManifestSHA256`, and `PlanRef` accessors (`:29-34`). The document says the plan store persists those three values (`:57`), but gives no method to obtain a `SnapshotPinRef` from `Pin`, nor accessors on `PinnedSnapshotRef`. As written, a caller cannot persist the durable pin identity returned by `Pin`; this blocks plan recovery. Make `Pin` return a durable `SnapshotPinRef` (and reserve `PinnedSnapshotRef` for the resolver-produced in-process reopen capability), or specify a bounded conversion/accessor API.

2. **The promised orphan/terminal pin lifecycle has no operation in the API.** In `docs/plans/verified-snapshot-lease-proposed-source-contract-2026-10-03.md`, the contract requires owner-confirmed orphan abandonment/release (`:65-67`) and tests forged-abandonment refusal (`:124`), while its exported API has no release, abandon, reconcile, or owner-disposition operation (`:25-41, :60`). It also explicitly defers terminal release pending an owner decision (`:67, :91`). A durable pin that can never be released cannot meet the stated crash-reconciliation requirements and can exhaust retained storage. Before source implementation, define the narrow recovery-owner handshake that reports authoritative committed/in-progress/abandoned state and permits releasing only the matching pin after identity checks and durable metadata update. Keep TTL/age-based deletion prohibited.

3. **The lease-to-plan identity and crash ordering do not line up with the recovery consumer contract.** `docs/plans/verified-snapshot-lease-proposed-source-contract-2026-10-03.md` requires a random `planRef` reserved before staging, pins to it, then persists a plan (`:65-67`). `docs/plans/recovery-planner-and-admission-proposed-contract-2026-10-03.md` instead persists `PLAN_PREPARED` with canonical plan hash and lease ID, then pins by plan hash, then publishes READY (`:247`); its planning sequence also describes obtaining/pinning before later binding the lease to the plan (`:261`). The older requested interface additionally pins by `(leaseID, owner, expires)` and exposes `Candidate(accountID)`/`LeaseID()` (`recovery-planner-and-admission-proposed-contract-2026-10-03.md:31-59`). The backup proposal exposes `Candidates()` and a different candidate method set, no `LeaseID`, no `OpenVerifiedArtifact`, and a lease `Restore` method (`verified-snapshot-lease-proposed-source-contract-2026-10-03.md:26-54, :43-49`). Freeze one compatible consumer contract: define whether the stable pin key is a preallocated operation/plan reference or final plan hash, the PREPARED/pin/READY order, and exactly which narrow artifact/restore operation recovery needs. The current split cannot be implemented independently without adapter and crash-boundary assumptions.

4. **Candidate projection loses a meaningful checkout state.** The current `checkout_attempts.session_id` column is nullable (`internal/hosted/store/migrations.go:18`). The proposed projection returns only `CheckoutRefs() []string` (`docs/plans/verified-snapshot-lease-proposed-source-contract-2026-10-03.md:43-49, :71-73`), so a snapshot with a checkout-attempt row whose session ID is NULL/empty is indistinguishable from a snapshot with no checkout row if both project to an empty slice. The recovery billing rules treat a present pending checkout row as unresolved and require exact snapshot/current checkout comparison (`docs/plans/recovery-planner-and-admission-proposed-contract-2026-10-03.md:249-253`). Add an explicit bounded presence/state bit or a typed nullable checkout reference, while continuing to omit request body, email, and credentials. A row with no usable provider session must remain a blocker, not look absent.

## Boundedness clarification before freeze

The contract rejects “oversized identifiers/references” but gives no byte ceilings for candidate customer/session refs or `planRef` (`docs/plans/verified-snapshot-lease-proposed-source-contract-2026-10-03.md:67, :71-73`); a 1 MiB metadata limit does not bound the size allocated while scanning an individual SQLite text value. Pin exact byte limits and canonical forms before implementation. Also define whether `MaxLeases` limits active handles/staging operations or all retained durable pins (`:20, :87-91`), and whether one store is intentionally bound to exactly one expected snapshot digest through `Inspection.ExpectedManifestSHA256` (`:16-20, :25-27`). Finally, separate declared artifact bytes from retained-byte accounting: `MaxLeaseBytes` includes metadata but must be no greater than the artifact-only `MaxDeclaredBytes` (`:17-20, :87`), so an artifact exactly at the inspection ceiling necessarily exceeds the lease ceiling once metadata is counted. State the effective acceptance formula and intended boundary behavior.
