# Independent review: recovery contract with terminal frozen accounts

**Ruling: HOLD for bounded code-ready implementation handoff.** The latest recovery contract resolves the prior epoch-wide availability blocker internally: it authenticates global effects before quiescence, permits a frozen-only global publication, records every account terminally, resumes forward after uncertain effects, and makes later activation one-account and guarded. Genesis and ordinary restart limitations are also stated explicitly and fail closed. However, the backup owner contract at `ac2367f7a033428217f68a0f1793fe40887716e2` still exposes an incompatible lease/pin lifecycle, and the recovery contract still has no executable path for an empty eligible set. These prevent a coordinated implementation from satisfying the described full recovery flow as written.

This ruling is about contract/code readiness only. It does not claim source authority, provider evidence, deployment readiness, or live qualification.

## What the revision now gets right

The global epoch approval is separately signed and binds plan/source, full sorted snapshot inventory and digest, eligible/allowlisted scope, old writer identity/generation/store, operation, action set, nonce, and expiry. `Begin` validates that approval and reopens/rechecks the pinned source before reservation or disruptive effects (proposal lines 85–107, 263, 271). It persists an effect-start marker before quiesce/stop, treats timeouts as uncertain, and allows only exact forward resume or a same-epoch continuation; it does not restart the old writer or restore revoked credentials (lines 15–17, 271).

The global restore now keeps all accounts frozen, makes every snapshot account terminal (`WITHHELD_FROZEN`, `ACTIVE_ELIGIBLE`, `DELETED`, or `DELETING`), allows commit when each has a terminal disposition rather than requiring all to be active, and prevents an account-level eligibility/approval failure from blocking service for other accounts (lines 13–17, 108–123, 265, 280–288). `ActivateOne` is explicitly separated after epoch commit, one account at a time, with an owner guard serializing account deletion/status/activation, exact restore marker, current provider/checkout/deletion checks, a final reread/CAS, and no restore/seal/adoption/publication side effects (lines 209–217, 287–292). These requirements are materially stronger and address the prior P0.

The proposal also explicitly says recovery admission only authorizes the first recovered startup; it does not invent journal genesis or admit a later unsealed G+1 tail. Ordinary restart remains fail-closed pending a separate journal/service handshake (lines 296–302). That is an acceptable scope boundary for a bounded recovery contract, but it blocks any claim that a deployed service is restart-ready.

## P0 — Recovery and backup lease/pin APIs and transaction order are not aligned

The recovery contract still defines its own lease/store seam, including `Stage(ctx, source, expectedDigest, options)`, `Reopen(ctx, leaseID, expectedDigest)`, `Pin(ctx, leaseID, owner, expires)`, and `Release(ctx, leaseID, owner)` (proposal lines 31–56). Its crash sequence writes a `PLAN_PREPARED` record with canonical plan bytes/hash and lease ID, pins by plan hash, then publishes READY (line 247). Planning also says to pin before provider observations and later release when no executable eligible plan exists (line 261).

The separately inspected backup proposal instead defines `SnapshotLeaseStore.Stage(ctx, sourcePath)`; `ReopenPinned(ctx, PinnedSnapshotRef)`; a lease-local `Pin(ctx, planRef)` returning a process-local pin handle; no store-level `Release` API pending owner decision; and a reserved random `planRef` that is pinned before the plan record is persisted (backup proposal lines 25–40, 57–67, 91–92). The backup flow intentionally handles a pin-before-plan crash as an orphan recovered using the reserved planRef. Recovery uses a leaseID/planHash owner model and plan-prepare-before-pin ordering. These shapes and crash protocols cannot both be implemented as the specified interfaces. The recovery `Release` path for zero-eligible/error cleanup also has no backup method to call. This is an owner-handshake mismatch, not evidence that either owner’s local algorithm is individually unsafe.

The candidate types also differ: backup exposes a sealed `VerifiedAccountCandidate` with a raw historical `SnapshotCustomerRef` and `CheckoutRefs`; recovery asks billing to consume its own `SnapshotIdentityCandidate` with a customer-binding candidate digest and `CheckoutReferences` (backup lines 43–50 and 71–75; recovery lines 167–177, 249–253). A recovery-owned adapter can safely convert the backup candidate to a historical-hint-only digest wrapper, but the contract must name that adapter and ensure only the billing owner can use it. The raw snapshot value remains a lookup hint, never verified account/customer authority.

**Required correction:** freeze one shared backup lease API and one crash order across both documents. Select one stable plan reference (for example, a recovery-store-reserved `planRef`), state whether the recovery prepare record precedes backup `Pin`, and define pin-before-ready and ready-before-return recovery. Add the owner-approved idempotent release/abandon operation needed for unpinned failures, zero-eligible outcomes, expired never-started plans, and terminal retention. Align method signatures/ref types exactly, or state explicit adapter types and their trusted owner. The staged lease must remain immutable and reopenable for the same digest/plan ref across crashes. Do not freeze either source lane until both proposals agree.

## P0 — Zero eligible accounts still cannot perform a frozen global recovery

The latest contract retains `ErrNoEligibleAccounts` with no executable plan (recovery proposal line 9). The planning sequence says a no-eligible outcome cannot enter `Begin` and requires a newly scoped executable plan or “separately reviewed frozen-only recovery path” (line 261). The frozen `RecoveryPlan.Validate` still rejects an empty account set (`internal/hosted/contracts/backup.go:306–308`), and `RecoveryPlan` is the only recovery request artifact identified by the proposed Begin/approval flow (proposal lines 203–207, 263).

That contradicts the new safe global behavior: every account can remain `WITHHELD_FROZEN`, and commit now requires terminal inventory dispositions, not an active account (lines 13, 283–287). When every approved candidate is ineligible, all accounts are outside scope, or the inventory contains only deletion dispositions, the operator still has no executable plan hash for the separately authenticated global frozen restore. In practice the service remains down despite a safe whole-snapshot frozen recovery being available in all other cases.

**Required correction:** keep `RecoveryPlan.Validate` unchanged, but define a distinct executable, non-activation-capable `FrozenRecoveryPlan`/epoch envelope bound to the verified source, exact full inventory, journal cut, old writer, and global epoch approval. It must authorize only frozen restore and recovered-start, never account activation. Alternatively, explicitly rule that zero-eligible recovery is an intentional service outage and remove the claim that this contract provides a complete frozen-recovery path. Do not turn the non-executable `NoEligibleAccounts` outcome into a `Begin` authority by implication.

## Remaining owner seam: later activation

The behavioral contract for activation is now clear, but the typed boundary is not fully wired. `RecoveryAccountActivator.ActivateOne` is declared (proposal lines 209–217), while `Coordinator.ActivateOne` is described separately (lines 287–290); the production `Config` shown earlier contains a read-only billing observer and whole-restore applier, but no service-owned account guard/CAS dependency (lines 125–138, 204–207). The text correctly says the billing/service owner must add an account-guard API or locked-observer variant (line 287); it should identify which package implements the interface and how the recovery CLI reaches that in-process guard. Existing service startup constructs handlers only after admission (`internal/hosted/service/service.go:334–365`), and the current concrete observer has its own per-account lock and read-only behavior (`internal/hosted/billing/recovery_observer.go:177–204`); that does not itself give a recovery CLI process the active service’s mutation lock.

This is an implementation handoff that can be resolved without changing the core state machine: define a service-owned `ActivateOne` request boundary (in-process or authenticated local RPC), its exact CAS/update transaction, and how it consumes the signed approval and billing/deletion evidence under the same guard as forget/delete. Keep SQL writes inside that service owner. The existing `RecoveryApplier` interface is tied to `RecoveryPlan`/`RecoveryApplyRequest` and its result consistency predicate (`internal/hosted/contracts/backup.go:332–390`); do not claim that interface directly serves post-commit activation unless an additive typed contract explicitly binds epoch, account, approval, and restore marker.

## Pin persistence, cleanup, cancellation, and startup boundary

Recovery’s new `PLAN_PREPARED` reconciliation is internally coherent if its referenced lease API supports it: only the exact prepared plan retries pin/publication, unreturned prepared work is resumed or explicitly abandoned, and an executable READY plan is not returned until pinned (proposal line 247). Backup’s own pin-before-plan flow is also internally coherent: reserve `planRef`, pin exact content, atomically persist the plan, repair orphan pins only after recovery-store abandonment (backup lines 57–67, 91–92, 124). The problem is alignment, not the individual crash models. Context-aware stage/read/close/cancel behavior is explicit in both (recovery lines 43–56, 247; backup lines 87–99, 123–126).

The genesis/restart limitation is explicit and fail-closed (recovery lines 296–302), so it is not a blocker to the requested bounded contract result. It remains a required separately reviewed service/journal prerequisite before any hosted acceptance or restart-readiness claim.

## Recommendation

Do not freeze a coordinated implementation on `5168c101` yet. Preserve its global approval, terminal frozen dispositions, forward-only resume, and guarded single-account activation design. Resolve the lease API/planRef/pin-release handshake with the backup owner and add an executable frozen-only plan path for the zero-eligible case. Then obtain a narrow service-owner activation contract for the in-process mutation guard. After those owner documents agree, repeat exact-head independent review. No source, provider, or live evidence is implied by this report.
