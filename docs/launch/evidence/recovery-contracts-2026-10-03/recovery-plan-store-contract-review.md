## A. Cancellation amendment — CLEAR, bounded scope

The cancellation protocol specifies the exact attempt tuple including `attemptVersion`, expected backup store identity, verified root/lock identity and generation, no-follow absence check under both backup locks, synchronous callback lifetime, one-shot atomic shared alias state, expiry on callback return, and consumption under the owner CAS lock before a durable cancellation tombstone. Exact retries recheck absence; canceled tuples remain tombstoned; N+1 requires explicit staging with a fresh lease ID. It rejects proof serialization, replay, changed store/lock, later attempts, and pin-present cases, and limits its guarantee against `unsafe` and process-memory compromise. This is a sufficient bounded contract to authorize a separately owned backup API amendment, after the relevant source owners adopt the API. It is not evidence that current backup code implements the proof.

The proposed bootstrap order is coherent at the behavioral level: preflight backup root/lock identity, persist that identity in the recovery superblock, then construct/reopen the backup store and compare identities before lifecycle operations. Current backup draft inspection confirms the mismatch being addressed: `CancelPinAttempt(ctx, attempt)` carries no absence proof; `SnapshotPinRef` has private fields with getters `ID`, `ManifestSHA256`, `PlanRef`, `ReservationVersion`; and `NewSnapshotLeaseStore(ctx, options, lifecycle)` accepts no preflight identity. `FindPinned` compares the attempt’s planRef, lease ID, digest, reservation version, and attempt version to the stored pinned lease before returning `pinRef`, whose ID is sourced from the lease record’s pin ID. The amendment must therefore be coordinated with backup ownership; no API has been implemented here.

## B. Full store contract — HOLD

1. **Construction order is narrative, not an implementable API contract.** The document proposes `PreflightSnapshotStoreIdentity(ctx, options)` and says the recovery store is constructed with the result before `NewSnapshotLeaseStore`, but neither a concrete production factory signature nor a transport/constructor signature for passing and validating the opaque identity is specified. Current backup constructor has no identity parameter. Specify the owner-selected factory and exact constructor signatures, including where recovery identity is durably bound and how backup reopening consumes/checks it, before source freeze.
2. **The state table omits a pinned-but-not-ready terminal path.** It allows `PINNED → READY` but no `PINNED → ABANDONED_BEFORE_EFFECTS`; prose says once pin exists abandonment is terminal at the recovery layer and release uses reconciliation, while `ReconcilePin` returns `PinKeep` for `PINNED` and the release rules require a terminal proof. Define the exact CAS and typed no-effects predicate that permits such a terminal disposition, or explicitly state that these pins can remain retained indefinitely and align the prose and state table. Do not infer release from pin presence/absence.
3. **Canonical wire contract is not frozen to golden schema.** “Fixed structs,” canonical JSON, tagged arms, and sorted slices are useful requirements, but the complete envelope/owner-record field order, exact tagged-arm encoding, and golden bytes/hash vectors are not specified in this proposal. These are explicitly left to source tests; define them before claiming the full contract is code-ready.
4. **Owner-owned construction dependencies remain unsupplied.** The document correctly names unresolved epoch authority, recovered-admission verifier, plan approval/source proof, writer/journal proof, and provider/effect evidence, and says construction fails closed without them. The relevant owners and concrete immutable readers/verifiers/key sources/admission constructor are not yet identified as accepted interfaces. This is a legitimate full-store blocker, not a reason to weaken the failure behavior.

The proposal does meaningfully specify append/CAS behavior, hash-domain separation, bounded/context-aware I/O, strict decoding, filesystem identity and sync protocol, crash/race cases, private proof requirements, cancellation tombstones, release authorization and backup terminal release mechanics. Those strengths do not resolve the constructor/API and pinned terminal-state gaps above. Keep the full store, epoch/admission, startup, provider, deployment, and acceptance gates open.
