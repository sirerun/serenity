## Blocking finding

**P1 — Eligible plan hash definition is cyclic or underspecified.** The proposal defines `EligibleRecoveryPlan` as embedding `contracts.RecoveryPlan`, then states `PlanHash` “hashes the entire envelope” and approval binds that final hash (`docs/plans/recovery-planner-and-admission-proposed-contract-2026-10-03.md:84-90`). The embedded `RecoveryPlan.PlanHash` is itself required to be a SHA-256 digest by the unchanged production contract (`internal/hosted/contracts/backup.go:269-282, 289-292`), and `Validate` authenticates bytes behind that field as the plan identity. If the embedded field is the envelope's final `PlanHash`, hashing the entire envelope includes the hash being computed, so no digest can be produced. If it is a separate digest, the proposal does not define its canonical input/domain, its relationship to the envelope digest, or which is the public `--plan-hash` / Apply request identity. An implementer could omit the embedded hash field from canonical bytes, hash only the nested plan, or assign the outer digest; these yield different identities and approval/store interoperability.

**Required correction:** specify two explicit domains if retaining both values: e.g. `RecoveryPlan.PlanHash = SHA256(canonical RecoveryPlan payload with its PlanHash omitted)` and `EligibleRecoveryPlan.EnvelopeHash = SHA256(canonical envelope containing that completed inner hash)`. State which exact digest is stored as immutable plan key, shown by CLI, bound by global epoch approval, passed to Apply, and used in all lifecycle CAS/read APIs. Or remove the duplicate hash from one layer through an additive contract amendment. Define analogous frozen-only domain for parity, and require tamper tests for both hashes and every payload field. Do not say “hashes entire envelope” if any field is excluded; enumerate exclusions and domain separators.
