## Blocking findings

1. **The journal-head reservation/activation protocol is still an open proof obligation.** The contract requires the authority to reject if the journal head changed between verification and activation, but `Prepared.ActivateWriter(ctx, head)` is an authority call with no defined atomic observation/fence against the object store ([proposal lines 54–65]([external evidence path]), [line 104]([external evidence path])). The proposed service method then takes a writable `DeletionJournal` and returns a `DeletionRead`, without defining the shared transaction/reservation handshake ([lines 108–125]([external evidence path])); it explicitly leaves “how authority reserves the verified head through writer activation/first append” for the service owner to specify (line 125). This is material because current `ReadThrough` can observe a changing tail and the active generation can be empty/unrepresented in `DeletionRead` ([journal.go lines 338–388]([external evidence path])). **Required correction:** get service, contracts, and journal owners to accept one concrete seam that binds the exact verified head *and active generation* to a durable reservation, prevents appends during proof/activation, and makes post-activation service replay validate that same reservation before publication. Define how an empty authorized successor generation is represented when the last visible watermark is the preceding seal. Do not leave this as an implementation-time “must specify” item.

2. **“Read-only” is not reflected in the proposed Go capability types.** `Prepared.ReadOnlyJournal` returns `contracts.JournalObjectStore`, whose API includes `PutIfAbsent` ([proposal lines 54–58]([external evidence path]), [deletion.go lines 148–197]([external evidence path])). The service seam accepts the full `DeletionJournal`, which includes `AppendDeletion` and `Seal` before admission completes ([deletion.go lines 238–242]([external evidence path])). A provider may promise not to use writes, but the type does not enforce the proposed “no writable credential before proof/activation” boundary. **Required correction:** define a read-only journal-object interface containing only `Get`/`ListAfter` and a distinct post-activation writer capability; make the staged admission API incapable of append/seal until activation succeeds.

3. **Restart has no usable source for its required authenticated invocation.** `Factory.Restart(ctx)` accepts no invocation and the trusted composition-root inputs listed for the factory do not include an invocation source ([proposal lines 24–35]([external evidence path])). Yet `Authority.PrepareRestart` requires `SignedRuntimeInvocation` ([lines 40–52]([external evidence path])). No interface or trusted injection path explains how those signatures connect. **Required correction:** define a trusted runtime-invocation provider (or pass a signed envelope into `Restart` with a strictly authenticated platform-only caller boundary), including issuer/audience/expiry and cancellation behavior. The authority must not silently infer identity from config or ambient environment.

4. **The restart fence does not yet enumerate and close every write-capable credential class for the namespace.** The requirement revokes credentials “for the prior writer,” including in-flight/renewable sessions ([proposal lines 81–87]([external evidence path])); it does not bound other principals or control paths that may write the same prefix. The journal contract itself identifies bucket role/policy, delete/version permissions, lifecycle, and conditional-write enforcement as separate obligations, not currently qualified facts ([deletion.go lines 148–188]([external evidence path])). **Required correction:** require an owner-reviewed inventory and enforcement proof covering every principal and credential route capable of mutation (workload and assumed-role sessions, refresh/renewal paths, alternate service/admin/break-glass principals, bucket/access-point policies, and mutation-capable automation). State which are revoked/denied and how provider policy prevents bypass during reservation and after new lease activation. A local timeout or journal collision is already correctly rejected as insufficient evidence.

## Source comparison and preserved boundaries

The source description is substantially accurate: `LifecycleDependencies` currently requires `Recovery`, while `AssembleWithDependencies` performs the admission read and full-history read and requires both reads to be sealed at the same watermark ([service.go lines 73–99]([external evidence path]), [lines 334–369]([external evidence path])); legacy constructors fail closed. The journal stores `WriterID` on entries and seals but `DeletionRead` currently returns only `Entries`, `To`, and `Sealed` ([deletion.go lines 115–125]([external evidence path]), [lines 199–213]([external evidence path])). `ReadThrough` validates the chain and may return an unsealed tail; `NewJournal`/`ProductionJournal` simply accept injected store, writer ID, generation, and clock ([journal.go lines 33–43]([external evidence path]), [lines 302–393]([external evidence path])).

The proposed `JournalWriterUse{Generation, WriterID}` is a sufficient identity key **if** writer IDs are globally unique per durable issuance as the proposal requires, and if extraction covers every verified entry and seal. That representation, first-use ordering, completeness on partial reads, duplicate treatment, and its mapping to authority records need to be frozen in the contracts/deletion owner request; today no production reader emits the field. The current source's seal objects carry `WriterID`, so extraction must include them too ([deletion.go lines 115–125]([external evidence path]), [proposal lines 91–102]([external evidence path])).

Keep `RecoveryAdmission` and its two sealed same-boundary reads unchanged. Current service shutdown has no lease and `Close()` only cancels/joins workers and closes gateway, pool, and DB ([service.go lines 470–483]([external evidence path])); the proposal correctly asks for a service-owned lease and context-aware ordered cleanup, but that owner seam must be frozen before implementation ([proposal lines 117–127, 138–141]([external evidence path])).
