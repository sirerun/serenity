## 2026 09 07 -- T1.34 closeout: the said/prefers confusion, named by specific held-out span, both directions

Task: docs/plans/E1-m1-ingest.md T1.34, minted by chief's T1.29 disposition ruling. Its acc line asks for a dedicated documented investigation naming the specific held-out spans where the model confuses `said` and `prefers`, plus either a fix that measurably improves `said`'s P/R or a founder-visible finding if no fix closes the gap. T1.29/PR #179 (previous entry) fixed the underlying confusion as part of its own critical path but left this row's own acc-line clause -- naming the specific spans, as a standalone artifact -- unclaimed, flagging it explicitly as a coordinator call. This entry is that write-up, verified directly against the real corpus and the real shipped code rather than reconstructed from any diagnostic tool's now-gone scratch output.

**Direction 1: `prefers` spans losing to `said` because a reporting verb introduces them.** Cross-checked `evals/corpora/ava/labels/ava-prefers-*.yaml` against the real `evals/corpora/ava/split.yaml` held-out set directly (24 of 44 `prefers` spans are held out). Every held-out span frames the preference through a reporting verb or an equivalent citation device rather than a bare "Ava prefers X" statement -- for example `ava-prefers-02` ("Ava mentioned in a team survey that she prefers dark roast coffee"), `ava-prefers-22`/`26`/`30`/`34`/`38` ("In a retro survey, Ava wrote that she prefers ..."), and `ava-prefers-23`/`27`/`31`/`35`/`39` ("Ava's assistant's briefing notes mention she prefers ..."). `internal/extract/extract.go`'s v4 `familyGuidance["prefers"]` now states the rule directly, naming the exact verbs: "Use 'prefers' (not 'said') whenever the content itself states something Ava prefers, regardless of the reporting verb introducing it (mentioned, wrote, noted, confirmed, said)." Measured effect: `prefers` moved from a failing measurement to recall_ci=[1.000,1.000] in PR #179's final acceptance run.

**Direction 2: `said` spans about a preference losing to `prefers`.** The `said` family's own corpus deliberately includes exactly this case: `ava-said-05` through `08` and their held-out siblings `ava-said-07`/`25`/`26`/`27`/`28` all report "Ava said she'd rather use feature flags than a hard cutover" through different framings (a meeting quote, an email, a Slack recap, a summary attribution) -- content that is a preference statement, attributed via "said." `familyGuidance["said"]` v4 now carries the mirror-image rule with this exact span as its own worked example: "Use 'said' (not 'prefers') whenever the span frames it as something Ava said/stated/was quoted saying, even when the content itself sounds like a preference" -- chunk: "In the sprint planning session, Ava said she'd rather use feature flags than a hard cutover." -> `{"predicate":"said","object":"prefer-feature-flags"}`. Measured effect: `said` moved from a failing measurement to recall_ci=[0.750,0.958] in the same final run -- not a clean [1.000,1.000], so this family's disambiguation is measurably improved, not perfected; the remaining shortfall traces to `said`'s two other, unrelated fixed clusters (verb-retention on "deploy-window-thursday", generic-noun-redundancy on "on-call-needs-fourth"), not this specific confusion.

**Both directions are now also enforced by a third, cross-cutting rule** (`buildPrompt`'s preamble, `internal/extract/extract.go`): "A sentence's reporting verb (said, stated, confirmed, mentioned, wrote, noted, quoted) is a narrative framing device, not itself evidence for the 'said' predicate: when the reported content matches a MORE SPECIFIC predicate already listed above ..., extract only that specific predicate." This is the general form neither per-family guidance line could be on its own, since the same reporting-verb-vs-specific-predicate confusion recurred in `committed_to` too (PR #179's own disclosure).

**T1.34's acc line, checked against this entry**: the documented investigation above names the specific held-out spans in both directions and why (shared reporting-verb/citation framing, disambiguated by whether the reported content matches a more specific predicate). The fix (PR #179, already shipped) measurably improves `said`'s P/R against the T1.32 corpus. Checkbox flipped below.

## 2026 09 07 -- T1.29 recall-bar closeout: all 12 ava families now pass, three real acceptance runs needed to get there

Task: docs/plans/E1-m1-ingest.md T1.29 (PR #179), scope as narrowed by T1.32/T1.33/chief's 2026-09-07 disposition: the pass bar is bootstrap recall lower bound >= 0.70 per family (`internal/eval/runner.RecallFloor`). Starting scope: the 4 families T1.32 left failing (`belongs_to_project`, `committed_to`, `prefers`, `said`). A 5th (`takes_medication`) came back into scope mid-task -- detail below.

**Method**: a throwaway diagnostic tool (`.claude/scratch/family-diag/main.go`, gitignored, not part of the acceptance gate) runs the real production extraction path (`internal/extract.Extractor` over `internal/router.OpenAICompatibleProvider`) against every held-out span for a chosen family filter, with `chat_template_kwargs.enable_thinking: false` (T1.31's mechanism) for roughly an order of magnitude faster per-call turnaround than the real thinking-on acceptance path -- useful for fast per-span root-cause iteration, explicitly NOT the acceptance measurement itself. Printed predicted-vs-golden per span, parsed by a small Python script into a match/total table per family plus a mismatch list.

**Findings, each concentrated in one phrasing cluster per family** (not a diffuse problem), with one exception found only by the real production path:

- `belongs_to_project`: two independent clusters.
  1. Names starting with a generic-sounding lead word ("Project Lighthouse", "Project Meridian") had that word inconsistently dropped, even though "Operation Tidewater" never lost "Operation" -- the prior guidance's own worked example never said to keep EVERY word of a name. Fixed by stating the verbatim rule explicitly plus a same-shape counter-example.
  2. **Invisible to the fast diagnostic entirely.** Two full-corpus disable-thinking re-runs both scored this family 24/24 clean. The first real thinking-on acceptance run showed it failing (recall_ci=[0.667,0.917], tp=19/fp=0/fn=5) -- all 5 misses were the exact same held-out cluster, "Ava's calendar invite series is titled after X." A targeted thinking-on-only diagnostic reproduced it directly: 4 of 5 spans in this cluster produced zero observations after 21-69s (every other span in the same run finished under 15s), and the 5th timed out entirely at 366s. Every other belongs_to_project phrasing, including three other equally indirect "extra"-block templates, extracted correctly and quickly. Reads as the model's thinking pass spending real time deliberating whether a meeting series named after a project counts as membership evidence -- disable-thinking's forced-fast mode never gives the model room for this hesitation, which is exactly why it never showed up there. **Lesson: a fast diagnostic that forces thinking off is not a substitute for the real acceptance path -- it can score a family perfectly clean while the production path genuinely fails it, because the failure mode itself only exists when the model is allowed to deliberate.** Fixed with an explicit rule plus a worked example stating this naming-convention evidence counts like a direct assignment statement; re-verified with a targeted thinking-on diagnostic (24/24, all sub-20s, no more timeouts or abstentions), then confirmed clean on a full live re-run (recall_ci=[1.000,1.000]).
- `committed_to`: "review-pr-by-friday" (all 5 held-out phrasings) dropped its deadline every time. First fix (a second worked example, no contrastive example) closed this cluster but broke the previously-clean "ship-q3-report" cluster -- caught only because the re-check re-ran the FULL 24-span family, not just the fixed cluster. **Methodological lesson (recurring from earlier in this same task): a narrow before/after check scoped only to the cluster you just fixed will not catch a regression you introduced elsewhere in the same family; always re-score the whole family.** Fixed for real by narrowing the "keep the deadline" exception to review commitments only, plus a third, contrastive worked example (ship-q3-report itself, same "by X" shape, deadline still dropped).
- `said`: two independent clusters, found across two diagnostic passes. "deploy-window-thursday" kept the reported clause's own verb ("should move to") instead of dropping it; fixed with a worked example on that shape. "on-call-needs-fourth" kept generic nouns ("rotation", "person") already implied by adjacent words in the slug ("on-call-rotation-needs-fourth-person" instead of golden's "on-call-needs-fourth") -- present in every prior diagnostic run too, just not flagged until a full-corpus re-check after the first `said` fix looked at every mismatch rather than only the cluster being targeted. Fixed with a fourth worked example plus a general rule (drop a generic noun once an adjacent word in the slug already implies it).
- `prefers`: 3 of 4 held-out spans using a reporting verb other than "said" itself ("mentioned", "wrote") to introduce a preference still lost to "said". Not family-specific -- the same failure shape recurs as one of `committed_to`'s misclassifications too. Real fix is a new cross-cutting instruction in `buildPrompt`'s preamble, not a per-family patch: a reporting verb (said, stated, confirmed, mentioned, wrote, noted, quoted) is narrative framing, not itself evidence for the "said" predicate, when the reported content matches a MORE SPECIFIC predicate already in the vocabulary list. `prefers`' own guidance restates the rule locally too, as reinforcement.
- `takes_medication`: **not one of the 4 originally-targeted families** -- T1.32/T1.33 both measured it passing with no guidance -- but the SECOND full acceptance run (after confirming the belongs_to_project fix) showed it newly failing (recall_ci lower bound 0.583, tp=18/fp=5/fn=6). Investigated rather than assumed to be sampling noise: found a real, reproducible pattern with a targeted diagnostic, the same shape already fixed twice above in this same task -- the model keeps an administration frequency/timing modifier the golden slug always drops ("Zyrtec daily" -> golden "zyrtec", model emits "zyrtec-daily"; "melatonin nightly" -> golden "melatonin"). One drug (albuterol) golden keeps "inhaler" (the product's delivery form, not a frequency word) while still dropping "as needed" -- confirms the rule is "drop timing/frequency wording", not "drop every modifier". Since T1.29's acc line names all 12 families, a family failing a real re-run puts it back in scope regardless of earlier scoping -- not a unilateral expansion. Fixed with a new guidance entry; re-verified 24/24 on a targeted diagnostic, then confirmed on the third, final live re-run (recall_ci=[1.000,1.000]).

**Also fixed T1.35** (filed by T1.32's author while cross-checking the expanded corpus, not built there -- folded into this task's critical path since none of the target families could be honestly re-measured while one family's own worked example leaks a held-out answer): `familyGuidance["prefers"]`'s example ("Ava prefers remote work on Fridays.") was itself one of the family's held-out spans, an RFC 0001 SS16 violation. Replaced with a genuine train-split phrasing of the identical fact, confirmed against the current `evals/corpora/ava/split.yaml` (not assumed).

**Regression guard added**: `TestFamilyGuidanceExamplesAreNeverHeldOut` regex-parses every `familyGuidance` value's `chunk: "..."` worked examples, loads the real `split.yaml` via `eval.LoadSplit`, and fails if any example's span is held out -- so a T1.35-shaped leak cannot recur silently. Verified red->green: `sed` temporarily reintroduced the exact T1.35 leak, confirmed the test fails with a clear diagnostic naming the offending example, restored via a `.bak` copy, reconfirmed green.

`PromptVersion` bumped v3 -> v4 (cache-busting: the whole guidance map changed).

**Three full `cmd/eval-runner -mode live` acceptance runs were needed** (thinking-on, real DGX `qwen3.8-27b` endpoint, the only measurement that actually gates this task), each detached (`nohup ... & disown`, confirmed `ps` PPID=1) with incremental checkpointing, per T1.32's established pattern -- and each one disclosed here rather than only the final result, since each surfaced a genuine gap the fix set had not yet closed:

## 2026 09 06 -- T1.31 full-corpus extraction throughput: root-caused and measured

Task: docs/plans/E1-m1-ingest.md T1.31, filed from docs/evals/m1-report.md's finding that `serenity extract all` over the real 92,586-chunk corpus projects to ~2-3 months at `qwen3.8-27b`'s observed per-chunk rate.

**Bottleneck, precisely measured against the live DGX SGLang endpoint** (`http://192.168.86.250:30000/v1`, same pod as T1.23's run): sent real extraction-shaped prompts (matching `internal/extract.buildPrompt`'s exact shape, one email-style chunk and one clinical-note-style chunk) via raw `chat/completions` calls, both with default settings and with `chat_template_kwargs: {"enable_thinking": false}` added to the request body.

| Chunk | Mode | Wall time | completion_tokens | reasoning_tokens | reasoning share |
|---|---|---|---|---|---|
| email (360 prompt tokens) | default (thinking on) | 57.7s (one earlier attempt hit a 120s client timeout entirely -- host-contention variance, consistent with T1.23's own report) | 1573 | 1471 | 93.5% |
| email | `enable_thinking: false` | 3.9s | 189 | 0 | 0% |
| clinical note (227 prompt tokens) | default (thinking on) | 20.1s | 774 | 494 | 63.8% |
| clinical note | `enable_thinking: false` (x2 trials) | 3.2s, 3.1s | 141, 146 | 0, 0 | 0% |

**Root cause: `qwen3.8-27b`'s default "thinking" reasoning pass, not sequential single-connection extraction.** Both are real (`internal/extract.Extract` does call `ExtractChunk` in a plain `for` loop, one chunk at a time, zero concurrency -- confirmed by reading the code), but the reasoning overhead dominates: it alone explains a 6-15x per-call wall-clock multiplier on these two samples, comfortably enough on its own to turn "a few days" into "~2-3 months" over 92,586 chunks at the default rate (92,586 x ~30-58s serial ≈ 32-62 days, matching the M1 report's estimate). Sequential-connection latency is a real, secondary, additive cost on top of this, not the dominant one.

**Not a content-parsing bug**: the SGLang server returns reasoning text in a separate `message.reasoning_content` field, never inline in `message.content` -- `internal/router.openAIMessage` only maps `content`, so `internal/extract.parseResponse` never sees the reasoning trace either way. This rules out "unparsed `<think>` tags breaking JSON decode" as a contributor to T1.28/T1.29's accuracy gaps; those remain a separate, real question this task does not answer.

**Extraction quality was not degraded on the two disable-thinking samples** -- both produced well-formed, schema-conformant JSON with the same (or a cleaner) set of observations as the thinking-mode run on the same chunk.

**Fix shipped, opt-in**: `internal/router.OpenAICompatibleProvider` gained `ExtraBody map[string]any`, merged verbatim into the outgoing request body when non-nil (nil by default -- a request is byte-identical to before this field existed). `internal/config.Models` gained `disable_thinking` (bool, `omitempty`, default false); `internal/providers.buildChatProvider` wires it to `ExtraBody: {"chat_template_kwargs": {"enable_thinking": false}}` for both the `openrouter`-selected and substring-inferred local-server paths, never for `AnthropicProvider` (no such concept) and never for `BuildEmbeddingRouter` (embeddings don't reason). This is deliberately NOT a default: a real OpenAI/OpenRouter endpoint (served by the same adapter) does not recognize `chat_template_kwargs` and some APIs reject an unrecognized top-level field outright, so a brain pointed at a real cloud provider must never send it un-opted-in.

**What this does not close**: even at the measured ~3-4s/chunk disable-thinking rate, a strictly sequential 92,586-chunk run is still ~90 hours (~3.75 days) of serial single-connection wall-clock -- from "not viable on any timeline" to "a viable background/overnight-scale run", not to "fast". Concurrency in `internal/extract.Extract`'s chunk loop (batching multiple in-flight requests to the same SGLang endpoint, which can typically serve several concurrent generations) is the next lever if a faster full-corpus run is ever needed, and is intentionally out of scope here -- it is a bigger, separate change to `internal/extract`'s core loop, not a config knob, and would need its own task and its own ordering-safety analysis (extraction has no cross-chunk state, so is safe to parallelize, but was not verified here).
