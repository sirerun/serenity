## T23.1: Review and merge the six-PR stack in order

### Objective

A reviewer sees `origin/main` at a new head that contains, in order, keyed
memory recovery (#220), the writer ownership lock (#221), fresh semantic
indexing with `search_state` (#222), `cancel_memory_operation` fencing
(#223), `read_memory_fact` exact read (#224), and `--credential-profile`
(#225). Every PR is merged, `main`'s CI is green at the final head, and
`hosted-status.md`'s pins table reflects the new `origin/main` SHA.

### Scope

This task authors no new source files. It reviews, rebases, un-drafts, and
merges six already-open PRs, and updates `docs/launch/hosted-status.md` and
this epic's checkbox. Out of scope: editing any PR's product code beyond
resolving a rebase conflict in that PR's own branch; registering any new
route or tool; touching `internal/server`, `internal/store`, `internal/writer`,
or `internal/index` beyond what each PR's own diff already contains.

### Design notes

No new types or APIs. Merge order is fixed by the existing stack, each PR
based on the previous head: #220 `4e3c4150f5`, #221 `3edf6d56b7`, #222
`5ccb30b45b`, #223 `86b0929da3`, #224 `57166d6678` (draft), #225 `1c2ac6b0df`
(draft). For each PR, in order:

1. Read the diff (`gh pr diff N`).
2. Confirm CI is green at the current head (`gh pr checks N`).
3. Post a review comment naming what was checked: tests present for the
   behavior change, no secret material introduced, no daemon-token or
   bearer-auth weakening in `internal/server` or `internal/server/mcp`.
4. Un-draft #224 and #225 before merging them (`gh pr ready N`).
5. Rebase-merge (`gh pr merge N --rebase`).
6. Retarget the next PR onto `main` (`gh pr edit N+1 --base main`) and wait
   for its CI to report green before repeating.

If a rebase conflicts, resolve it in a worktree on that PR's own branch and
push there; never force-push `main`. If any PR's CI turns red after
retargeting, stop merging further PRs and record the failure in
`hosted-status.md` under Blockers before continuing.

### Acceptance criteria

- `gh pr view 220 221 222 223 224 225 --json state` all report MERGED,
  `origin/main` contains the `cancel_memory_operation` and
  `read_memory_fact` tool registrations and the `--credential-profile`
  flag, and the first `ci` run on `main` after the last merge is green.
- Each PR was merged in stack order (220 through 225); no PR was merged
  before the one it was rebased onto.
- #224 and #225 are no longer draft at merge time.
- `hosted-status.md`'s pins table records the new `origin/main` SHA and
  marks T23.1 done in Active ownership.
- No behavior change is authored by this task itself (it only lands
  already-reviewed diffs), so there is no genuine-red case for this task's
  own code. The falsifiable check instead: if a PR's post-merge `ci` run on
  `main` is red, that PR did not actually merge clean and T23.1 is not
  done until it is fixed and green, not silently marked complete.

### Verification

For each PR: `gh pr checks N` before and after retargeting. After the last
merge, on `main`: claim the build lease
(`CLAIM_REMOTE=/Users/Shared/mini-build-lease.git ~/.claude/skills/claim/scripts/claim.sh claim R-build-lease --purpose "T23.1 post-merge verify"`),
run `go vet ./...`, `go build ./...`, `go test -race -timeout 600s ./...`,
`golangci-lint run --timeout=10m`, then release the lease. Confirm
`origin/main`'s `ci` workflow run for the final merge commit is green via
`gh run list --branch main --limit 1`.
