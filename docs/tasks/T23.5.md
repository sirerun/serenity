## T23.5: Brain provisioning state machine

### Objective

A reviewer sees that asking for an account's brain is idempotent and
crash-safe: calling it twice at once, or once and again after a simulated
crash between allocation and readiness, always ends with exactly one
`ready` brain row and one on-disk directory. A deleted brain's directory
is gone and `Provision` never returns it.

### Scope

Create `internal/hosted/provision/` only: `provision.go` (the
`Provisioner` type and `Provision` method), `provision_test.go`. Depends
on `internal/hosted/store` (T23.4) for the `brains` table. Out of scope:
no HTTP, no pool/runtime-opening logic (T23.8), no credentials (T23.6);
does not create or open a Serenity brain's internal git/index structure
itself beyond `os.MkdirAll` for the directory -- opening the brain runtime
for reads/writes is T23.8's job.

### Design notes

Package `github.com/sirerun/serenity/internal/hosted/provision`. This
task provisions exactly one brain per account for the launch slice (plan
v1's multi-brain limits, e.g. Builder's 3, are a later-wave concern once
billing exists; this task's own scope is "the account's one default
brain," not general multi-brain allocation).

`Provisioner{Store *hoststore.Store, BrainsRoot string}` with
`Provision(ctx context.Context, accountID string) (Brain, error)`:

1. In one transaction, attempt `INSERT INTO brains(id, account_id, state, path_key, created_at) VALUES (?, ?, 'allocating', ?, ?)` guarded by a partial unique index
   `CREATE UNIQUE INDEX brains_account_active ON brains(account_id) WHERE deleted_at IS NULL`
   (SQLite supports partial indexes) -- this is the "one non-deleted brain
   per account" invariant for this task's scope. A concurrent second
   `Provision` call hits the UNIQUE constraint, meaning it lost the race;
   it falls through to step 3 instead of erroring.
2. The winner commits the `allocating` row, then `os.MkdirAll(filepath.Join(p.BrainsRoot, id), 0o700)`,
   then updates the row to `state = 'ready', ready_at = now`. If the
   process crashes between the `allocating` commit and the `ready` update,
   the row is left `allocating` with no guarantee the directory exists.
3. Any caller (the original loser, or a fresh call after a crash) that
   finds an existing row for the account: if `state = 'ready'`, return it.
   If `state = 'allocating'`, resume it -- `os.MkdirAll` is idempotent, so
   re-running step 2's directory creation and state update is safe and
   completes the interrupted transition rather than creating a second
   directory or row.
4. If `state = 'deleted'`, `Provision` does not resurrect it; this task
   does not implement re-provisioning after deletion (T23.25 owns
   deletion semantics; a fresh `Provision` call here for a fully deleted
   account is out of scope until that task exists).

Directory path is `filepath.Join(BrainsRoot, brainID)`, never derived from
any caller-supplied value (ADR 014: "no request supplies a path ... that
selects storage").

### Acceptance criteria

- Calling `Provision(ctx, accountID)` twice concurrently, and again after
  a simulated crash between directory creation and the `ready` update,
  yields exactly one `ready` brain row and one directory.
- A brain marked `deleted` is never returned by `Provision` and its
  directory is absent after purge.
- The partial unique index on `brains(account_id) WHERE deleted_at IS NULL`
  exists and is exercised by the concurrency test (two goroutines calling
  `Provision` with the same `accountID` at once).
- Genuine red: remove the `allocating` row write (call `os.MkdirAll` and
  the `ready` update directly without the guarding `INSERT` step) and run
  the concurrent test; record that it creates two directories and two
  `brains` rows for one account. Restore the `allocating` write, rerun,
  and record exactly one directory and one row.
