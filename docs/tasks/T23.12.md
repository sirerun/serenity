## T23.12: Slice proof harness

### Objective

A reviewer runs one command against a local `serenity hosted serve`
behind a local Caddy and sees, for two independent accounts: dev-mode
magic-link login, provisioning, credential issue, a real Node MCP client
doing `remember` then `recall` by paraphrase, a process restart, `recall`
again finding the same fact, and a cross-account attempt at
`recall`/`remember`/`forget` that is denied -- with a JSON receipt written
to disk that later tasks (T23.17, `hosted-acceptance.md`) cite as
evidence.

### Scope

Create `internal/hosted/harness/` (`main.go`, a `go run`-able driver) and
`scripts/hosted/slice.sh` (starts a local Caddy in front of a local
`serenity hosted serve`, runs the harness, tears both down). Add a small
Node fixture under `internal/hosted/harness/mcpclient/` (a package.json
pinning `@modelcontextprotocol/sdk` and a short script using
`StreamableHTTPClientTransport` with Rakazo's exact headers) used only by
this harness, not shipped as product code. Register a CI job `hosted-slice`
in `.github/workflows/ci.yml` running this harness against an in-process
`serenity hosted serve`. Out of scope: no product code changes; this task
is integration glue over T23.5, T23.6, T23.7, T23.9, T23.10, T23.11, none
of which it modifies.

### Design notes

`go run ./internal/hosted/harness` (aliased by `scripts/hosted/slice.sh`)
against a `serenity hosted serve` instance reachable either directly
(local dev) or through a local Caddy reverse proxy fronting it (closer to
production, and the only way to test "Caddy serves `/mcp` at its final
URL with no redirects" -- ADR 014). For each of two accounts:

1. Dev-mode login: with `SERENITY_HOSTED_DEV=1` and the server bound to
   loopback, `RequestLink` prints the raw token to the server's stderr
   (T23.9's `DevSender`) instead of sending real mail; the harness reads
   it from the server process's captured output rather than parsing an
   email.
2. `Consume` the token, `StartSession`, hit `GET /` to trigger
   `Provision`, `POST /connect` (or the equivalent programmatic path
   T23.10 exposes) to `Issue` a credential with write scope.
3. Spawn the Node MCP client (`internal/hosted/harness/mcpclient`) using
   the official SDK's `StreamableHTTPClientTransport` against
   `<origin>/mcp`, with headers `Authorization: Bearer <raw>` and
   `Accept: application/json, text/event-stream`, `redirect: manual` (any
   3xx is a harness failure) -- the exact shape ADR 014 documents Rakazo's
   real adapter sending. `remember` one fact with distinctive paraphrase-
   friendly wording, then `recall` it using different words than the
   original fact to prove semantic (not just lexical) retrieval.
4. Restart the `serenity hosted serve` process (SIGTERM, relaunch),
   `recall` again with the same client, confirm the fact is still found.
5. Using account B's credential, attempt `recall`, `remember`, and
   `forget` against account A's brain id or session id (however the
   gateway is addressed -- there is no brain id in the URL per ADR 014,
   so this step attempts to reuse account A's session id under account
   B's credential, the exact cross-account case T23.7 tests at the unit
   level); assert every one is denied.

Write a JSON receipt (`internal/hosted/harness` output, one file per run)
recording: timestamps, both accounts' ids (not emails), the fact text and
its recall latency, the restart-recall result, and the cross-account
denial results. `hosted-acceptance.md` and T23.17 cite this file's path,
not its content inline.

The harness account is explicitly not proof of a real signup (state this
in the receipt) -- it isolates failures in the slice itself, separate
from T23.32's real-browser timing runs and T23.34's real-Rakazo-client
memory-quality proof.

### Acceptance criteria

- `go run ./internal/hosted/harness` (or `scripts/hosted/slice.sh`)
  against a local `serenity hosted serve` behind a local Caddy performs,
  for two accounts, the full sequence above: login, provisioning,
  credential issue, remember/recall by paraphrase, restart, recall again,
  and a denied cross-account attempt.
- The run writes a JSON receipt file that names its own path in stdout.
- The Node client uses the real `@modelcontextprotocol/sdk` package
  (pinned version), not a hand-rolled HTTP client mimicking it.
- The CI job `hosted-slice` runs this harness on every push/PR the same
  way `gbrain-protocol-conformance` runs its own external-client
  conformance check (network access for `bun install`/`npm install` is
  acceptable here the same way it already is for that job).
- Genuine red: point the harness's cross-account step at the gateway with
  the session-generation check disabled (a temporary one-line change
  mirroring T23.7's own genuine-red case), rerun the harness, and record
  that the cross-account `recall` wrongly succeeds. Restore the check and
  record the corrected denial.

### Verification

before the PR, capturing its output. `go vet ./internal/hosted/harness/...`.
